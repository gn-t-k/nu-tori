# git の操作

- WIP コミットは、PR を出す前に工程ごとのコミットにまとめる。amend したブランチは `git push --force-with-lease origin <今のブランチ>` で上げ直し、コロンで別のブランチを指さない。許可のルールは `claude/x:<別のブランチ>` の形を確かめずに通すため（`docs/agents/tooling.md` の「許可のルール」）
- まとめ直し（`git reset`・`git commit --amend`）と push は、`&&` でつながず、別の Bash の呼び出しで送る

  **Why:** `git reset --soft origin/main && git commit ... && git push --force-with-lease ...` を1つのコマンドで送ると、auto mode に Git Destructive として拒まれた。分けて送ると通った（#905）
- 実装を終えたら、開発者の許可を待たずに、下の「PR の前のレビュー」を通して PR を出す。`/implement` などのスキルがコミットで終わっていても、PR まで進める。PR を出すことと merge することは別で、merge は下の行のとおり言われたときだけにする

  **Why:** PR を出してよいか聞いて止まったセッションが、開発者の返事まで約18時間待った。受け入れ条件に PR の本文の証拠があったセッションは PR まで出していて、どちらが正しいかが文書に無かった（#934）
- 同じファイルを触る PR は、並んで実装してよい。いくつものセッションが衝突の解消で渋滞したら、開発者が交通整理のセッションを1つ立て、そこが順に解いて merge する。開発者に交通整理がいると言われたセッションは、自分では衝突を解かない
- 積み重ねた PR の前の PR を直したら、後ろのブランチに merge で取り込む。後ろのブランチを rebase すると、レビュー済みの差分とコメントの位置がずれるため
- PR を merge するのは、開発者に言われたとき（「CI が通ったら混ぜて」など）だけにする。merge は許可のルールで確かめずに通るので、止めるものはこの決まりだけになる
- PR の本文は `/pr` の形で、日本語で書く。レビューの結果や、ほかの文書が PR の本文に書くよう求めること（実機の確認、App Privacy の回答）は、その後ろに節を足して書く
- 見た目が変わる PR（アプリの画面、`site/` のページ）は、変えた画面のスクリーンショットを PR の本文の Evidence に置く。push で見た目がまた変わったら撮り直す
  - アプリ: 変えた画面で `attachScreenshot(of:named:)` を呼ぶ UI テストを回し、その画像を使う。呼ぶテストが無ければ、その画面を通る UI テストに足す。クラウドのセッションでは、手で始めた `ios-ui-test.yml` の回の成果物 `ios-ui-test-report` から取る（通った回にも上がる）
  - `site/`: ブラウザで開いて撮る（Linux では入っている Chromium と Playwright）
  - 置き方: Mac のセッションは下の `--attach` で添付する。クラウドのセッションは添付できないので、画像を Artifact（claude.ai の非公開のページ）に載せ、そのリンクを書く。CI の成果物は3日で消えるので、成果物のリンクで済ませない

  **Why:** 見た目の変更を、開発者がスクリーンショットで確かめられないまま PR が merge できる状態になっていた（#710）
- Issue・PR に画像や動画を添付するときは、`gh` の `--attach` を使う（使い方は `--help`）。ファイル名は英数字にする（macOS は濁点を分けた形で持ち、本文の `./ファイル` の参照と一致せず書き換わらない）。添付してよいのは、開発者の健康データが写っていないものだけ（ルートの `AGENTS.md` の「公開リポジトリ」）

## PR の前のレビュー

PR を出す前と、PR に push する前に、下の小見出しの2つのレビューのうち、ブランチが変えたものにかかるものを通す。手順は2つで同じ。

- `git fetch origin <マージ先のブランチ>` を済ませてから、かかるレビューのサブエージェントを同時に立て、マージ先のブランチと、2周目か push の前ならそのレビューの照らしたコミット（前の周の返事の1行目か、PR の本文のそのレビューの節にあるもの）を渡す。サブエージェントが fetch すると、auto mode が外への書き込みと見て止めることがある。読む文書と返す形は、それぞれの定義（`.claude/agents/<名前>.md`）にある
- サブエージェントは、手元の `origin/<マージ先のブランチ>` をそのまま使い、次の範囲を照らす
  - 照らしたコミットを受け取らなかったとき（PR を出す前の1周目）: `git diff origin/<マージ先のブランチ>...HEAD`
  - 照らしたコミットを受け取ったとき（2周目と、PR に push する前）: 照らしたコミットより後に、このブランチで書いた変更だけ。`git log -p --no-merges <照らしたコミット>..HEAD ^origin/<マージ先のブランチ>` と、衝突を解いた merge コミットごとの `git show --remerge-diff <コミット>`
- 挙がった箇所を直したら、そのレビューの新しいサブエージェントを立て、1周目の返事の1行目にある照らしたコミットを渡して、直した分をもう一度照らす。周はレビューごとに数え、どちらも2周まで。2周目で挙がった箇所の扱いは、それぞれの小見出しにある
- main や前のブランチを取り込んだだけの push（衝突の解消も手直しも無い merge）では照らさず、`scripts/check` だけを通す
- PR の本文に、レビューごとの節（`## 好みのレビュー`、`## ポリシーの照合`）を置き、結果（0件か、直した箇所と、残して開発者の判断を待つ箇所）と照らしたコミットを書く。push のたびに更新する

**Why:** 周を重ねるたびに前の周で見なかった行へ新しい指摘が出て、0件まで5周かかるチケットが続いた。取り込みのたびに PR 全体を照らし直してもいて、マージの間隔が延びていた。

### 好みのレビュー

コード・テスト・依存・エージェントが読む文書（置き場は `CODING_STANDARDS.md` の「文書」）を変えたブランチで通す。サブエージェントは `preferences-review` で、差分を `CODING_STANDARDS.md` に照らす。2周目で挙がった箇所のうち、コメント・名前・並び順のようにその場で閉じるものは直して、照らさずに push する。振る舞いや設計にかかるものは直さずに PR の本文に書き、開発者の判断を待つ。

**Why:** 2周目の指摘を開発者に聞くと、名前やコメントの直しは毎回「直す」と返り、聞く往復だけが増えていた。

`/implement` と `/implement-spec` の中で `/code-review` を呼ぶときは、Spec の軸のサブエージェントだけを立てる。好みを照らすのは好みのレビューだけにする。最後のまとめの `## Standards` には、好みのレビューに任せたと1行書く。開発者が自分で `/code-review` を呼んだときは、スキルのとおり2つの軸を回す。

**Why:** 2つのレビューが同じ文書で同じ差分を照らし、同じ指摘が2回出たり（#605）、指摘が食い違ったり（#744）、1つの `///` を3往復したりしていた（#714）。照らす場所を1つにした（#791）。スキルは `skills-lock.json` の中にあって直せないので、ここに書く。

### ポリシーの照合

コードか依存を変えたブランチで通す。エージェントが読む文書だけを変えたブランチでは通さない。サブエージェントは `policy-review` で、差分をプライバシーポリシー・利用規約・特商法の表記と、`docs/agents/privacy.md` の決まりに照らす。

指摘には「直す」か「開発者の判断」の印が付き、周に関わらず印で扱う。「直す」は同じ PR で直し、2周目のものは照らさずに push する。「開発者の判断」は1周目でも直さずに、`## ポリシーの照合` の節に書いて開発者を待つ。App Privacy の回答の表を載せるのもこの節にする。

**Why:** `docs/agents/privacy.md` の決まりを守るのが実装役に任されていて、照らす仕組みが無かった。変更が入るところで照らし、ずれを main に入る前に止める（#911）。

## 動かして確かめる

アプリかサーバーの振る舞いを変えたブランチは、「PR の前のレビュー」と同じとき（PR を出す前と、PR に push する前）に、アプリを動かして触れた機能を確かめる。サーバーは `verify-server` スキル（`.agents/skills/verify-server/`）で確かめる。

1. 差分から、触れた機能を地図の索引（`.agents/skills/verify-<アプリ>/features/README.md`）で引く
2. その機能のファイルにある入口をすべて通す
3. 機能を足した、入口や見え方を変えたときは、同じ PR で地図を直す（機能のファイルの形は `.agents/skills/verify-<アプリ>/MAP-FORMAT.md`）
4. PR の本文の `## 確かめ` に、機能と入口ごとに、した操作と見えた結果と、確かめたコミットを書く
5. 動かせない入口は「確かめていない」と書き、どこで確かめるかを書く。確かめる場所は、各 `verify-<アプリ>` スキルの「確かめられないとき」にある。クラウドのセッションの iOS は Mac のセッションで確かめる

文書だけの変更と、main や前のブランチを取り込んだだけの push では回さない。iOS の地図はまだ無いので、アプリの変更は 5 のとおり書く。

**Why:** テストと好みのレビューが通っても、本物の経路で機能が動くかは、merge のあとの `main-flow-on-development` まで分からなかった。`/implement` の中だけに置くと、`/diagnosing-bugs` からの直しや小さな直しが通らないので、PR のゲートに置いた（#902）。

## クラウドのセッションで GitHub を操作する

Claude Code on the web のセッション（`CLAUDE_CODE_REMOTE=true`）では、GitHub への通信がプロキシを通り、プロキシが認証を差し込む。

- `GH_TOKEN` には仮の値 `proxy-injected` が入っていて、本物のトークンはプロキシが差し替える。PAT を環境変数に置かない
- GraphQL は PR 用の一部を除いて 403 になり、GraphQL を使う `gh issue ...` や `gh pr ...` は通らない。`gh api repos/<owner>/<repo>/...` の REST を使う
  - 読む: `gh api repos/gn-t-k/nu-tori/issues/<n>`、コメントは `.../issues/<n>/comments`
  - サブ Issue: `.../issues/<親>/sub_issues`（追加は `-X POST -F sub_issue_id=<子の DB ID>`）
  - 依存関係: `.../issues/<n>/dependencies/blocked_by`（追加は `-X POST -F issue_id=<ブロック元の DB ID>`）。すでに張られていると 422「already been taken」が返る
  - 担当者・ラベル・状態: `.../issues/<n>/assignees`、`.../issues/<n>/labels`、`-X PATCH .../issues/<n> -f state=closed`
- 画像や動画は添付できない（試した結果は #357）。添付が要るときは、開発者に頼むか、`mcp__ccd_session__spawn_task` で Mac のセッションを始めるカードを出す
- Issue とコメントを書くと、リンクやコードの前後にバッククォートが足されたり、バッククォートが引用符に変わったりして、書式が崩れることがある（コメントの投稿でも Issue の本文の更新でも、`gh api` でも `mcp__github__*` でも起きた）。書いたら必ず `scripts/diff-posted <元の本文のファイル> <API のパス>` で読み直し（API のパスの書き方は引数なしで出る）、崩れていたら手元に置いた元の本文で書き直す。コメントは `mcp__github__update_issue_comment`、Issue の本文は `gh api -X PATCH .../issues/<n> -F body=@<ファイル>` で直し、もう一度読み直す。空白の無い日本語の文に `[名前](URL)` を埋めると、URL を含む長い語として囲まれやすい。直らないときは、参照の形（文中は `[名前][33]`、末尾に `[33]: URL`）にする。ただし行頭の `- [名前][33]: 本文` は参照の定義と取られて崩れるので、その形の行は文中に URL を書く
- Dependabot へのコマンド（PR へのコメントで送る recreate など）は送れない。コメントや本文に書くと、文字のあいだに「·」（U+00B7）が入って崩れ、Dependabot に届かない（`gh api` でも `mcp__github__*` でも起きた。外す設定は文書に無い。#395）。開発者に頼む
- ワークフローのやり直しは `gh api -X POST repos/gn-t-k/nu-tori/actions/runs/<id>/rerun`（落ちたジョブだけなら `.../rerun-failed-jobs`）でできる（#394）
- ほかのツール（Codex、Cursor、Dependabot）が作った PR の CI の失敗は、その PR のブランチで始めたセッションで直す。クラウドのセッションは、作業ブランチにだけ push できるため
- `mcp__github__*` のツールも使える。Issue、サブ Issue、コメント、PR は扱えるが、依存関係のツールは無いので `gh api` で張る
