# コーディングの好み

言語に寄らない好みを書く。言語ごとの当てはめは `docs/agents/languages/<言語>.md` にあり、そこで置き換えると書いた箇所はそちらに従う。

## コードを説明する情報

- 実装の仕様はテストに書く
- 変更の理由はコミットメッセージに書く
- コメントは、実装から読み取れない事情があるときと、長い関数や、状態管理・暗黙の依存のように読み解きの助けが要るときだけ書く。その前に、コードを直して読み取れるようにできないかを探す
- コメントは日本語の1行で書く。改行は人が必要と思ったときに入れる

**Why:** コメントは実装とずれていく。仕様はテストに、理由はコミットに置けば、ずれない。

## 名前は具体的な振る舞いを表す

- `get` や `make` のような汎用の動詞を機械的に選ばず、入力から何をどう返すのかが伝わる名前を、候補を比べて選ぶ
- 動詞を処理の種類に固定しない。ドメインと呼び出し側の文脈から決める

例: 体重記録の列から体重の傾向を計算する関数

- `getWeightTrend`: 保存済みの値を読むのか、その場で計算するのか分からない
- `fetchWeightTrend`: `fetch` は外からの取得を表すので、手元の記録から計算する処理に合わない
- `computeWeightTrend`: 手元の記録から計算して返すことが分かる

## ファイルと公開するもの

- 1つのファイルからは、公開するもの（型、関数、コンポーネント）を1つだけ出し、ファイル名をその名前に揃える
- 1ファイル1つより責務のまとまりを優先する。型と、その型にだけ意味を持つ整形・判定は、同じファイルに置く。複数の型で独立した意味を持つようになったら切り出す
- 対になる・並行する責務は、対称な名前で揃える（例: 2つの表示のしかたと、それぞれの外枠）。片方を読めば他方の責務が分かる

## ファイルの中はトップダウン

- ファイルの先頭に、そのファイルが公開するものを置き、内部の型・関数・定数は下にまとめる
- 型やコンポーネントの中も、外から使うものを上に、内部のものを下に置く
- 互いに参照するものは、段落ごとにまとめて近くに置く

**Why:** 外から使うものが先に目に入り、詳細が後ろに来るほうが読み解きやすい。

## 定数は最小のスコープに置く

- 1つの関数・コンポーネントの中でしか使わない定数は、その中に置く
- 複数の箇所で共有する値、型やモジュール全体の決まりを表す値、ドメインの名前を持つ値だけを、型やモジュールのスコープに置く

**Why:** 定義を使う場所に近づけると依存の範囲が分かり、モジュール全体で意味を持つ値と見分けやすい。

## 設計の単位は責務で決める

ファイルやコンポーネントを分けるときは、分けた単位が独立した責務を説明できることを基準にする。ファイル分割や1ファイル1つを満たすためだけに、値を受け取って下に渡すだけのコンポーネントを作らない。

### 状態は論理状態の数で型を作る

真偽値に限らず、相関する複数のフィールドを並べる前に、組み合わせの数と論理状態の数を数える。表現できるが起こり得ない組み合わせがあるなら、タグ付きユニオンにし、値はその値が意味を持つ場合にだけ持たせる。

例: 読み込み中か（真偽値）、エラー（無いこともある）、記録の列（無いこともある）を並べると8通り書けるが、起こり得るのは「読み込み中」「失敗（エラーを持つ）」「読み込み済み（記録の列を持つ）」の3つ。3つの場合を持つタグ付きユニオンにすれば、読み込み中なのにエラーがある、といった組み合わせを書けなくなる。

正本の状態と、そこから一意に導ける状態を、同じ型や API の別々のフィールドとして受け渡さない。導出値は、その判断に責任を持つ境界で計算し、境界を越える状態の表し方を1つにする。

### 値が無いことを許すのは、必要な事情があるときだけ

フィールド・引数に値が無いことを許す（optional、nullable、省略できる引数）前に、値が無くなるドメイン上の事情を1つ挙げる。挙げられないなら必須にする。

- 理由のない省略は、意味のない「未指定」を書けるようにし、値が無いときのフォールバックの分岐を呼び込む
- 機能が未実装といった段取りの都合を、API の省略に持ち込まない。未実装の間は、呼び出し側でプレースホルダを渡して吸収する
- 常にある枠で、中身が空になり得るものは、「値か、空」を必ず渡させる形にし、渡し忘れを型で見えるようにする

**Why:** 起こり得ない状態を型で書けなくするという、上の節と同じ考え。

### 関数は処理の流れで分ける

- 分けた先の処理が独立した責務（成功と失敗、作成と更新など）なら、振る舞いごとに別の関数にし、呼び出し側で分ける。`fakeFetch(delay, shouldFail)` ではなく、`fakeFetchSuccess(delay)` と `fakeFetchFailure(delay)` にする
- 同じ流れを通り、違いがデータの形だけなら、タグ付きユニオンを1つの関数で受ける
- 自分たちのタグ付きユニオンで分けるときは、すべての場合を書き、場合を足したときに漏れが型エラーになる形にする（既定の枝を置かない、網羅の検査を足す、など）

**Why:** 形（真偽値の数、場合の数）で分けると、同じ責務を分けすぎたり、違う責務を無理にまとめたりして、どちらも保守しにくくなる。「分岐を管理する責務」と「特定の処理をする責務」を別のものとして見る。

## ドメイン知識の置き場

- 計算・判定・検証の決めごと（ドメイン知識）は、既定でサーバーの TypeScript のドメイン層に書く
- 端末（Swift）に書くのは、ADR-0011 の基準に当たるものだけにする。「端末で計算したほうが楽」は理由にしない。端末とサーバーの両方に要るものの置き方も ADR-0011 に従う
- ドメイン層は、実行基盤の型や API に触れない。ドメイン層が要る置き場と外への呼び出し（記録の置き場、写真の控え、LLM の提供元など）は、ドメイン層が型を定め、基盤に固有の層（Durable Object、D1・R2・LLM の提供元・Apple の API への入出力）がそれを実装する
- 1人の記録を読み書きするドメインの処理は、その人の Durable Object の中で動かす（ADR-0012）。Durable Object のクラスは、ドメイン層を呼ぶ入口（HTTP から、アラームから）と、ドメイン層が定めた記録の置き場の実装だけを持つ薄い層にする
- HTTP の受け口は、記録を読み書きする要求なら、セッションを確かめてその人の Durable Object を呼ぶだけにする。まだセッションのないサインインと、アカウントの削除（Apple のトークンの取り消し、D1・Durable Object・R2 の控えを消す）は、受け口の Worker でドメイン層を呼ぶ

**Why:** 知識が2か所にあると、片方だけ直してずれる。ドメイン層を基盤から切り離しておくと、基盤を移るとき（ADR-0012 の出口）に書き直すのが基盤に固有の層だけで済む。

## キャストのいらない形を探す

型のキャストが要る形になったら、「型推論が複雑だから」で済ませず、関数の構造、別の API、型パラメータ、型の設計を見直して、キャストなしで型が通る形を探す。

**Why:** キャストは型の食い違いを隠し、将来の型エラーを見逃させる。

## 新しい技術を選ぶ

- 旧世代になった技術（旧いプロトコル、非推奨のライブラリなど）の置き換えで、移行の手間を却下の理由にしない
- 新しい技術で実現できない機能があるときだけ、その制約を示して、旧来のものを残す案を出す。「使う場面が限られるから」は残す理由にしない

**Why:** 古いものは性能と保守で不利になり、公式の支援が先に途切れる。いずれ移行を迫られるなら、早いほど累積の手間が少ない。

## 依存パッケージ

- 依存は、そのとき最新の版を、範囲指定ではなく厳密な版で固定する
- 最新の版は、パッケージの配布元（レジストリやリポジトリのタグ）で確かめる。記憶にある版で決めない
- 新しい版が出たら追って、常に最新に保つ
