# コーディングの好み

## コードを説明する情報

- 実装の仕様はテストに書く
- 変更の理由はコミットメッセージに書く
- コメントは、実装から読み取れない事情があるときと、長い関数や、状態管理・暗黙の依存のように読み解きの助けが要るときだけ書く。その前に、コードを直して読み取れるようにできないかを探す
- コメントは日本語の1行で書く。改行は人が必要と思ったときに入れる

**Why:** コメントは実装とずれていく。仕様はテストに、理由はコミットに置けば、ずれない。

## 名前は具体的な振る舞いを表す

- `get` や `make` のような汎用の動詞を機械的に選ばず、入力から何をどう返すのかが伝わる名前を、候補を比べて選ぶ
- 動詞を処理の種類に固定しない。ドメインと呼び出し側の文脈から決める

例: 体重記録の列から体重の傾向を計算する関数

- `getWeightTrend(from:)`: 保存済みの値を読むのか、その場で計算するのか分からない
- `fetchWeightTrend(from:)`: `fetch` は外からの取得を表すので、手元の記録から計算する処理に合わない
- `computeWeightTrend(from:)`: 手元の記録から計算して返すことが分かる

## ファイルと型

- 1つのファイルには、トップレベルの private でない型（または関数）を1つだけ置き（`private`・`fileprivate` の型と `#Preview` は数えない）、ファイル名をその名前に揃える（`WeightTrend.swift` → `struct WeightTrend`、`TimelineView.swift` → `struct TimelineView`）
- 1ファイル1型より責務のまとまりを優先する。型と、その型にだけ意味を持つ整形・判定は、同じファイルの extension に置く。複数の型で独立した意味を持つようになったら切り出す
- 対になる・並行する責務は、対称な名前で揃える（例: 2つの表示のしかたと、それぞれの外枠）。片方を読めば他方の責務が分かる

## ファイルの中はトップダウン

- ファイルの主役の型を先頭に置き、private な型・関数・定数は下にまとめる
- 型の中も、外から使うもの（View なら `body`）を上に、private な計算プロパティや下位の View を下に置く
- 互いに参照するものは、段落ごとにまとめて近くに置く

**Why:** 外から使うものが先に目に入り、詳細が後ろに来るほうが読み解きやすい。

## 定数は最小のスコープに置く

- 1つの関数・View の中でしか使わない定数は、その中に置く
- 複数の箇所で共有する値、型全体の決まりを表す値、ドメインの名前を持つ値だけを、型の `static` やファイルのスコープに置く

**Why:** 定義を使う場所に近づけると依存の範囲が分かり、型全体で意味を持つ値と見分けやすい。

## 設計の単位は責務で決める

ファイルや View を分けるときは、分けた単位が独立した責務を説明できることを基準にする。ファイル分割や1ファイル1型を満たすためだけに、値を受け取って下の View に渡すだけの View を作らない。

### 状態は論理状態の数で型を作る

Bool に限らず、相関する複数のプロパティを並べる前に、組み合わせの数と論理状態の数を数える。表現できるが起こり得ない組み合わせがあるなら、enum にし、値はその値が意味を持つ case にだけ持たせる。

```swift
// 8通り表現できるが、起こり得るのは3状態（読み込み中なのに error がある、などが書けてしまう）
struct WeightRecordsState {
    var isLoading: Bool
    var error: (any Error)?
    var records: [WeightRecord]?
}

// 3状態を enum で表し、起こり得ない組み合わせを書けなくする
enum WeightRecordsState {
    case loading
    case failed(any Error)
    case loaded([WeightRecord])
}
```

正本の状態と、そこから一意に導ける状態を、同じ型や API の別々のプロパティとして受け渡さない。導出値は、その判断に責任を持つ境界で計算し、境界を越える状態の表し方を1つにする。

### optional は必要な事情があるときだけ

プロパティ・引数を optional にする前に、nil になるドメイン上の事情を1つ挙げる。挙げられないなら non-optional にする。

- 理由のない optional は、意味のない「未指定」を書けるようにし、nil のときのフォールバックの分岐を呼び込む
- 機能が未実装といった段取りの都合を、API の optional に持ち込まない。未実装の間は、呼び出し側でプレースホルダを渡して吸収する
- 常にある枠で、中身が空になり得るものは `let caption: String?` にして、呼び出し側に nil を明示させる。`var` の optional は memberwise init に `= nil` が付き、渡し忘れが型で見えなくなる。引数の `= nil` も同じ

**Why:** 起こり得ない状態を型で書けなくするという、上の節と同じ考え。

### 関数は処理の流れで分ける

- 分けた先の処理が独立した責務（成功と失敗、作成と更新など）なら、振る舞いごとに別の関数にし、呼び出し側で分ける
- 同じ流れを通り、違いがデータの形だけなら、enum を1つの関数で受ける
- 自分たちの enum を switch するときは、すべての case を書き、`default` を置かない。case を足したときに、漏れがコンパイルエラーになる

```swift
// 成功と失敗という別の責務を、Bool で1つの関数の中に抱えている
func fakeFetch(delay: Duration, shouldFail: Bool) async throws -> [WeightRecord]

// 振る舞いごとに別の関数にし、呼び出し側で分ける
func fakeFetchSuccess(delay: Duration) async -> [WeightRecord]
func fakeFetchFailure(delay: Duration) async throws -> [WeightRecord]

let records = outcome == .success
    ? await fakeFetchSuccess(delay: delay)
    : try await fakeFetchFailure(delay: delay)
```

**Why:** 形（Bool の数、case の数）で分けると、同じ責務を分けすぎたり、違う責務を無理にまとめたりして、どちらも保守しにくくなる。「分岐を管理する責務」と「特定の処理をする責務」を別のものとして見る。

## キャストのいらない形を探す

- `as!` は使わない
- `as?` や `as!` が要る形になったら、「型推論が複雑だから」で済ませず、関数の構造、別の API、型パラメータ、protocol、enum を見直して、キャストなしで型が通る形を探す

**Why:** キャストは型の食い違いを隠し、将来の型エラーを見逃させる。

## 新しい技術を選ぶ

- 旧世代になった技術（`ObservableObject` に対する `@Observable`、XCTest に対する Swift Testing（Swift Testing で書けない UI テストは XCUITest のまま）、完了ハンドラに対する async/await など）の置き換えで、移行の手間を却下の理由にしない
- 新しい技術で実現できない機能があるときだけ、その制約を示して、旧来のものを残す案を出す。「使う場面が限られるから」は残す理由にしない

**Why:** 古いものは性能と保守で不利になり、公式の支援が先に途切れる。いずれ移行を迫られるなら、早いほど累積の手間が少ない。

## 依存パッケージ

- Swift Package の依存は、そのとき最新の版を `exact:`（Xcode では「Exact Version」）で固定する。`from:` や「Up to Next Major」の範囲指定にしない
- 最新の版は `git ls-remote --tags <パッケージのリポジトリの URL>` で確かめる。記憶にある版で決めない
- 新しい版が出たら追って、常に最新に保つ
