# レビューと検査

PR を出す前と PR に push する前に、ブランチの変更に何がかかるかと、どう回すかと、照合の1周の費用を置く。何にかかるかの正本は、下の「何にかかるか」の表にする。各道具の定義（レビュー役、検証スキル、`steward`）には回し方だけを置き、かかる条件はこの表を指す。

## 言葉

- **検査**: 機械が通る・落ちるを決めるもの。`scripts/check`（lint の規則、テスト、文書の重なりの検査を含む）と、それを回す CI のジョブ、UI テストの全件の回
- **照合**: レビュー役が差分を文書に照らすもの。好みのレビュー（`preferences-review`）、ポリシーの照合（`policy-review`）、文書の照合（`docs-review`）、仕様の照合（`/code-review` の Spec の軸）
- **設計の照合**: 実装の前に、設計の案を `codebase-design` に照らすもの。PR の時点の照合と時点も手順も違い、下の「何にかかるか」の表と「照合の回し方」の外にある（下の「設計の照合」）
- **確かめ**: アプリやサーバーを動かして見るもの。`verify-server`、`verify-ios`
- **敵役の試し**: 敵役のサブエージェントが差分を壊そうと走らせ、走らせて示せた不具合だけを残すもの。pstack の `interrogate`（下の「敵役の試し」）

## 何にかかるか

1つのブランチが複数の行に当たるときは、当たった行のものをすべて通す。照合の列の仕様の照合は、かける条件と回す回数がほかの照合と違う（下の「仕様の照合」）。

| 変更の種類 | 検査 | 照合 | 確かめ | ほかに PR の前にすること | merge の条件 |
| --- | --- | --- | --- | --- | --- |
| サーバーのコード・テスト | `scripts/check server`、CI の `server` | 好みのレビュー、ポリシーの照合、仕様の照合 | 振る舞いを変えたら `verify-server`。API の境目にかかる変更は、下の「端末とサーバーをつなぐ確かめ」も | 下の「サーバー」と「サーバーと iOS の両方」 | 開発者が言ったとき。`scripts/merge-tier` が `フェーズ1` と返す差分は下の「フェーズ1」 |
| iOS のコード・テスト | `scripts/check ios`、CI の `ios`・`ios-app`・`ios-version`。UI テストか画面の経路を変える PR は、PR の先頭のコミットで UI テストの全件（PR の CI では走らない。`ios/AGENTS.md` の「確かめる」） | 好みのレビュー、ポリシーの照合、仕様の照合 | 振る舞いを変えたら `verify-ios`（Mac のセッションだけ）。API の境目にかかる変更は、下の「端末とサーバーをつなぐ確かめ」も | 下の「iOS」「サーバーと iOS の両方」「iOS と site」 | 開発者が言ったとき。`scripts/merge-tier` が `フェーズ1` と返す差分は下の「フェーズ1」。UI テストの全件がかかる PR は、その結果が PR の本文の `## 確かめ` にそろってから（`steward` が見る） |
| `site/` | `scripts/check site`、CI の `site` | 好みのレビュー、ポリシーの照合、仕様の照合 | 無い（下の「知られている漏れ」） | 下の「site」と「iOS と site」 | 開発者が言ったとき。`scripts/merge-tier` が `フェーズ1` と返す差分は下の「フェーズ1」 |

| 依存（作業のブランチで変える） | 依存を置く対象の `scripts/check` と CI のジョブ | 好みのレビュー、ポリシーの照合、仕様の照合 | 振る舞いを変えたら、その対象の確かめ | 下の「依存」 | 開発者が言ったとき |
| エージェントが読む文書（`scripts/agent-docs-duplicates` がエージェントが読む文書とするものと、`.claude/agents/` を指すだけの `.codex/agents/`） | CI の `scripts` の文書の重なりの検査（`scripts/agent-docs-duplicates`） | 文書の照合、仕様の照合 | 回さない | 下の「文書」 | 開発者が言ったとき。`scripts/merge-tier` が `フェーズ1` と返す差分は下の「フェーズ1」 |

### ほかに PR の前にすること

文書を読んだ実装役に任された決まり。決まりの文は元の文書にあり、ここは、いつ読むかと置き場だけを指す。

- サーバー
  - `server/` か `shared/` で、端末に何がいつ届くかを変えるとき: 下の「敵役の試し」（照合の1周目の前に1回）
  - LLM の指示を変えたとき: `server/AGENTS.md` の「テスト」（評価を回し、要約を PR の本文に貼る）
  - D1・Durable Object の移行を足すとき: `server/AGENTS.md` の「DB」（並んで足す移行どうしは互いに頼らない）
- iOS
  - 見本の場面を足す・変えるとき: `ios/AGENTS.md` の「見本の場面」（値を LP とそろえ、作り物だけにする）
  - 送り待ちの置き場の形を変えたとき: `docs/agents/ios-mac.md` の「置き場の移行を実機で確かめる」（merge の前に開発者が実機で確かめる）
  - ヘルスケア・カメラ・通知・写真の読み込みに触れた PR を出すとき: `docs/agents/ios-release.md` の「実機の確認」
- サーバーと iOS の両方
  - 端末とサーバーの両方に置く決めごとを変えるとき: `docs/agents/shared-rules.md`（「今は片側だけの決めごと」の一覧の抜けを見る）と、下の「敵役の試し」
  - 記録の種類を足す、送り待ちのキーを足す・消すとき: `docs/agents/sync.md` の「記録の種類の足し方」と「置き場の約束」
  - 集めるもの、送り先、使い道、残る期間を変えるとき: `docs/agents/privacy.md` の「ポリシーを実装に合わせて保つ」（App Privacy の回答が変わる PR は、マージしたら #861 に表を足す）
- iOS と site
  - 見た目が変わるとき: `docs/agents/git.md` の、見た目が変わる PR のスクリーンショットの行
- site
  - 公開のページを書く・直すとき: `docs/agents/privacy.md`
- 道具
  - `@nu-tori.app` を差出人にして送る道具を足すとき: `docs/agents/tooling.md` の「`nu-tori.app` からメールを送る」（SPF・DKIM と、確かめる Issue）
- 依存
  - 版を上げるとき: `docs/agents/dependencies.md`
- 文書
  - 節を移した・消したとき: `docs/agents/decisions.md` の移し先の表

### 判断なしに通す変更

開発者を待たずに merge する変更。

- 依存の PR（Dependabot と `update-swift-packages.yml` が出す、依存の版だけを上げる PR）: patch と minor は、`check.yml` のジョブが全部通ると（必須でない `ios-app` を含む）`dependency-pr.yml` がマージし、壊れたら知らせで気づいて戻す。major は人が変更履歴を読んでマージする。照合と確かめはかけず、SDK の更新にもポリシーの照合はかけない。条件と戻し方は `docs/agents/dependencies.md`
- 調べもののチケットの PR（`docs/research/`）: CI が通ったらエージェントが merge する（`docs/agents/issue-tracker.md` の「調べもののチケットを終える」）
- 振る舞いを変えない PR のうち、パスで決まるもの: 下の「フェーズ1」

#### フェーズ1

当たるかは `scripts/merge-tier`（引数はマージ先のブランチ。既定は `main`）が、マージ先から分かれたあとの差分のパスで決める。実装役は自分で決めない。当たるのは、エージェントが読む文書だけ、テストを足すだけ（既存のテストを書き換えない・消さない）、`scripts/`・CI・道具だけの差分。その置き場にあっても、ゲートを弱めうるものと、用語・見た目・覆しにくい決定に触る差分は当たらない。フェーズ1に入れないパスの正本は `scripts/merge-tier --list` の一覧にする。

出力の1行目で分ける。

- `フェーズ1`: PR を出したセッションか、それを引き継いだセッションが、下の条件をそろえて merge する
- `待つ`: 開発者が merge を言う。2行目からに、差分のパスごとの理由がある
- `調べもの`: `docs/research/` だけの差分。`docs/agents/issue-tracker.md` の「調べもののチケットを終える」のとおりにする

merge の条件:

1. `check.yml` のジョブが全部通った（必須でない `ios-app` を含む）
2. 上の表でかかる、push のたびに回す照合と確かめの節（`## 好みのレビュー`、`## ポリシーの照合`、`## 文書の照合`、`## 確かめ`）の照らしたコミットが、PR の先頭のコミットか、先頭からたどって、main や前のブランチを取り込んだだけの merge コミット（上の「照合の回し方」で照らさない push）だけをさかのぼった先のコミット
3. `## 仕様の照合` の節がある。PR を出す前に1回だけ回すので、照らしたコミットは先頭でなくてよい
4. どの節にも、開発者の判断を待つ指摘が残っていない
5. 上の表の、当たった行の「ほかに PR の前にすること」と merge の条件の列の求めること（UI テストの全件など）が済んでいる

push で差分が変わるので、merge する直前に PR の先頭のコミットで `scripts/merge-tier` を回し直す。PR の本文の最後に次の節を置き、push のたびに更新する。`待つ` と `調べもの` の PR は、フェーズの1行だけを書く。

```markdown
## merge の条件

- フェーズ: フェーズ1（`scripts/merge-tier` を <コミット> で回した）
- [x] `check.yml` のジョブが全部通った（`ios-app` を含む）
- [x] 照合と確かめの節が先頭のコミットを照らしている
- [x] `## 仕様の照合` の節がある
- [x] 開発者の判断を待つ指摘が残っていない
- [x] ほかの文書が merge の前に求めること: <無い、または済ませたこと>
```

壊れたとき: 下の「merge のあとに気づくもの」で、エージェントが merge したフェーズ1の PR が壊したと分かったら、その PR を revert する PR を出す。フェーズ1はサーバーに出るコードを変えないので、`server/AGENTS.md` の「デプロイ」の、前の版のコードに戻さない決まりには当たらない。revert の PR の merge も、`scripts/merge-tier` のフェーズで決める。

**Why:** merge が開発者に言われたときだけで、文書だけの PR も返事を待って止まっていた。#939 で範囲を言葉で書いて実装役に任せ、#949 で決まりにはしないと戻した。自己申告をやめ、確かめられる条件にした。ゲートを弱める変更が開発者を通らずに入らないよう、ゲートそのものは外した（#1000）。

## 照合の回し方

PR を出す前と、PR に push する前に、上の表でブランチの変更にかかる照合を通す。下の手順は好みのレビュー、ポリシーの照合、文書の照合のもので、仕様の照合は回す回数と道具が違う（下の「仕様の照合」）。

- `git fetch origin <マージ先のブランチ>` を済ませてから、かかるレビューのサブエージェントを同時に立て、マージ先のブランチと、2周目か push の前ならそのレビューの照らしたコミット（前の周の返事の1行目か、PR の本文のそのレビューの節にあるもの）を渡す。サブエージェントが fetch すると、auto mode が外への書き込みと見て止めることがある
- サブエージェントは、返事の最初の行に、照らしたコミット（`git rev-parse HEAD`）と指摘の件数を書く。読む文書と、ほかに返すものと、指摘の並べ方は、それぞれの定義（`.claude/agents/<名前>.md`）にある
- サブエージェントは、手元の `origin/<マージ先のブランチ>` をそのまま使い、次の範囲を照らす
  - 照らしたコミットを受け取らなかったとき（PR を出す前の1周目）: `git diff origin/<マージ先のブランチ>...HEAD`
  - 照らしたコミットを受け取ったとき（2周目と、PR に push する前）: 照らしたコミットより後に、このブランチで書いた変更だけ。`git log -p --no-merges <照らしたコミット>..HEAD ^origin/<マージ先のブランチ>` と、衝突を解いた merge コミットごとの `git show --remerge-diff <コミット>`
- 挙がった箇所を直したら、そのレビューの新しいサブエージェントを立て、1周目の返事の1行目にある照らしたコミットを渡して、直した分をもう一度照らす。周はレビューごとに数え、どれも2周まで。2周目で挙がった箇所の扱いは、それぞれの小見出しにある
- main や前のブランチを取り込んだだけの push（衝突の解消も手直しも無い merge）では照らさず、`scripts/check` だけを通す
- `/implement-spec` の draft PR は、チケットを取り込むたびには照らさない（下の「`/implement-spec` の draft PR」）
- PR の本文に、レビューごとの節（`## 好みのレビュー`、`## ポリシーの照合`、`## 文書の照合`）を置き、結果（0件か、直した箇所と、残して開発者の判断を待つ箇所）と照らしたコミットを書く。push のたびに更新する

**Why:** 周を重ねるたびに前の周で見なかった行へ新しい指摘が出て、0件まで5周かかるチケットが続いた。取り込みのたびに PR 全体を照らし直してもいて、マージの間隔が延びていた。

### 好みのレビュー

サブエージェントは `preferences-review` で、差分を `CODING_STANDARDS.md` に照らす。2周目で挙がった箇所のうち、コメント・名前・並び順のようにその場で閉じるものは直して、照らさずに push する。振る舞いや設計にかかるものは直さずに PR の本文に書き、開発者の判断を待つ。

**Why:** 2周目の指摘を開発者に聞くと、名前やコメントの直しは毎回「直す」と返り、聞く往復だけが増えていた。

### ポリシーの照合

サブエージェントは `policy-review` で、差分をプライバシーポリシー・利用規約・特商法の表記と、`docs/agents/privacy.md` の決まりと、観測の道具に記録の中身を送らない決まり（ルートの `AGENTS.md`）に照らす。

指摘には「直す」か「開発者の判断」の印が付き、周に関わらず印で扱う。「直す」は同じ PR で直し、2周目のものは照らさずに push する。「開発者の判断」は1周目でも直さずに、`## ポリシーの照合` の節に書いて開発者を待つ。App Privacy の回答の表を載せるのもこの節にする。

**Why:** `docs/agents/privacy.md` の決まりを守るのが実装役に任されていて、照らす仕組みが無かった。変更が入るところで照らし、ずれを main に入る前に止める（#911）。

### 文書の照合

サブエージェントは `docs-review` で、照らす範囲で変わった文書を全体で読み、`writing-for-agents` と `docs/agents/decisions.md` の「置き場の観点」に照らす。照らす範囲の外の行への指摘は、1周目では挙げ、2周目では、直した分と重なるか食い違う行のものだけを挙げる。2周目で挙がった箇所のうち、言い回し・指す先・並び順のようにその場で閉じるものは直して、照らさずに push する。働き方や決定の置き場を変えるものは直さずに PR の本文に書き、開発者の判断を待つ。

**Why:** 好みのレビューが差分を `writing-for-agents` に照らしたあとに、どの文書にも無い「writing-for-agents の観点のレビュー」が文書の全体を読み、毎回1〜11件を足していた。重複や食い違いは、差分だけを読むレビューでは見つからないので、範囲の外の行も挙げる。照らす役を1つにした（好みのレビューが照らさない文書は `CODING_STANDARDS.md` の冒頭にある。#991）。

### 仕様の照合

差分を、結びつく Issue の受け入れ条件に照らす。上の表で仕様の照合がある行に当たり、Issue に結びつくブランチ（Issue を閉じる、または Issue に応える PR）は、`/implement` を通らない PR（`/diagnosing-bugs` からの直しや小さな直し）でも回す。

- いつ: PR を出す前に1回。push のたびには回さない。`/implement`・`/implement-spec` の中で回した1回がこの1回に当たり、PR の前にもう一度は回さない
- 何で: `/code-review` の Spec の軸のサブエージェントだけを立て、`origin/<マージ先のブランチ>...HEAD` を照らす。`/implement`・`/implement-spec` の中で `/code-review` を呼ぶときも同じにし、最後のまとめの `## Standards` には、好みのレビューに任せたと1行書く。開発者が自分で `/code-review` を呼んだときは、スキルのとおり2つの軸を回す
- 結果: PR の本文の `## 仕様の照合` に、照らした Issue と、結果（0件か、直した箇所と、残して開発者の判断を待つ箇所）と、照らしたコミットを書く。結びつく Issue が無いブランチは、無いと1行書く

**Why:** `/implement`・`/implement-spec` の中で1回回るだけで、`/diagnosing-bugs` からの直しや小さな直しでは回らず、結果を書く節の名前も「Spec のレビュー」「仕様のレビュー」とばらついていた（#989）。好みを照らさないのは、2つのレビューが同じ文書で同じ差分を照らし、同じ指摘が2回出たり（#605）、指摘が食い違ったり（#744）、1つの `///` を3往復したりしていたため（#714、#791）。スキルは `skills-lock.json` の中にあって直せないので、ここに書く。

### 1周の費用

照合を足す・絞るか、レビュー役が読む文書を変えるかを決めるときに比べる基準。測り直したら、この節の測った日・差分・表と、「何が数字を決めているか」の数字をまとめて置き換える。

2026-11-11 の main で、merge 済みの PR の差分を今の main の上に作り直し、上の表でかかる照合を1周ずつ回して測った（#996）。差分は、文書が #1010（8ファイル、+61/−9）、サーバーが #950（8ファイル、+175/−77）、iOS が #890（7ファイル、+235/−22）。

- 文脈: 終わったときの文脈の大きさ（サブエージェントの終わりの知らせの `subagent_tokens`）
- 延べ: 呼び出しごとに読ませたトークンと書いたトークンの合計（ほとんどはキャッシュから読んだ分）
- 時間: 終わりの知らせの `duration_ms`。10体を同時に立てたので、1体ずつより長めに出ている

## 敵役の試し

下の「かかる変更」に当たる変更に、PR を出す前に1回、pstack の `interrogate` を回す。

### かかる変更

`server/` か `shared/` の差分が、次のどれかの振る舞いを変えるときにかける。

- 同期の帳簿: `server/src/domain/sync-ledger/`、`/v1/sync/*` の受け口（`server/src/http/sync-routes/`）、種類が帳簿に渡すもの（`decide`、`whenGone`、今の値を読む口。置き場は `docs/agents/server-sync-ledger.md`）
- 状態の変更を足す時機: 端末の書き込みの外で変更を足す場所（記録の変化を書く入口の `run`・`addChange`、`decide` の `addedChanges`、推定と返事の書き込みの口）と、それを動かすアラームの時機。足す場所を増やす・減らす、足す条件や時刻を変える差分
- 端末とサーバーの両方に置く決めごと: `docs/agents/shared-rules.md` の決めごと（`shared/` の JSON と、サーバーでそれを使う関数）

かけないもの: iOS のコード、`site/`、文書、`scripts/`・CI・道具、上のどれにも当たらないサーバーの変更（LLM の指示、観測、同期を通らない受け口など）。上に当たっても、振る舞いを変えない作り替えには、まだかけない（#1001）。

### 回し方

`interrogate` は Skill ツールでは呼べない。ルートの `AGENTS.md` の pstack の行と同じ置き場から `skills/interrogate/SKILL.md` を読み、スキルのとおりに回して、次のところだけ変える。

- いつ: 実装をコミットしたあと、照合の1周目の前に1回。push のたびにも、直したあとにも回し直さない。`/implement-spec` では、draft を ready にする前に統合の差分に1回。敵役が文脈の上限で止まったら、かかるチケットごとに回し直す（#999 では、数百ファイルの統合の PR をコミットに絞って回した）
- 範囲: `origin/<マージ先のブランチ>...HEAD`。チケットごとに回すときは、そのチケットを取り込む前の統合ブランチの先から取り込んだあとの先まで（`<前>..<後>`）で、下の取り出す端は `<後>` にする
- 敵役: 2体。どちらも `model` と effort を渡さず、セッションのモデルの既定の effort で立てる。`arena` の Phase A の3の既定（1体目を `claude-opus-5-5-xhigh`）には従わない
- 置き場: 敵役ごとに worktree を分け、範囲の新しい端（HEAD のコミット）を detached で取り出し、依存を入れて（`server/` で `pnpm install`）から渡す
- 意図: `in-your-own-words` で、Issue の受け入れ条件、コミットのメッセージ、PR の本文の案から言い直して渡す。敵役には Issue と PR と、取り出したコミットより後の履歴（ほかのブランチを含む）を読ませない。意図を親の言い直しの1つにそろえ、ほかで書かれた穴や直しを手がかりにさせないため
- 指摘の確かめ: 敵役が示したコマンドを、実装役が自分の作業ツリーで走らせ直す。出力が壊れを示し、それが意図を破るものを残し、ほかは捨てる。残したものは直すか、直さない理由を書く

結果は PR の本文の `## 敵役の試し` に書き、push しても書き直さない。

- 照らしたコミット（チケットごとに回したときは、チケットと `<後>` の並び）と、渡した意図
- 残した指摘ごとに、コマンド、出力、どう意図を破るか、見つけた敵役、直したか直さない理由
- 敵役ごとの捨てた指摘の数と理由
- 敵役ごとのトークン（終わりの知らせの `subagent_tokens`）と時間（`duration_ms`）

**Why:** あとで不具合が見つかったサーバーの変更3つに回すと、直した道とは別の道（外す向き、文章だけ、週の見直し）で端末に届かないまま残る不具合（#871、#881 の1つ目）を、2体とも再現つきで見つけた。照合と `verify-server` には別の道を走らせて探す役がいない。敵役1体の文脈（`subagent_tokens`）が10万〜24万、2体で30万〜40万になり、並べて15〜22分かかる（#999 で測った。延べは測っていない。上の「1周の費用」の文脈と比べる）ので、PR の前に1回だけにする。`xhigh` は費用が1.3〜1.9倍、時間が最大9倍で、主な不具合の当たりは変わらなかった。2体にするのは、別々の体が同じものを見つけた変更と、片方だけが見つけたものがある変更があったため（#999、#1011）。不具合の軸のレビュー役は足さない。走らせて示せない指摘を足すだけになりそうなため。

## 設計の照合

新しいモジュールやインターフェースを足す設計の案を、1回照らす。足すモジュールもインターフェースも無い案では回さない。

- 時点: `/to-spec` で継ぎ目のスケッチを開発者に確かめる前と、`/tdd` で継ぎ目を開発者に確かめる前
- 新しい文脈のサブエージェントを1体立て、案（足すモジュールの名前と置き場、インターフェースの型と関数、継ぎ目の置き場、継ぎ目に入るアダプタ）と、関わる今のファイルのパスを渡す。案を選んだ理由は渡さない
- サブエージェントは `.agents/skills/codebase-design/SKILL.md` を読み、案を、深さ、継ぎ目の置き場、消してみる試し（deletion test）、継ぎ目にアダプタが2つあるかに照らす。指摘ごとに、観点、案のどこか、直し方を返す
- 直した案を開発者に見せ、直さなかった指摘は理由を添えて一緒に見せる

**Why:** 設計の指摘が出るのはコミットのあとの好みのレビューが最初で、開発者はインターフェースの設計のたびに「`codebase-design` の観点でレビューして」と手で頼んでいた（#980 の漏れ10）。スキルは `skills-lock.json` の中にあって直せないので、ここに書く。

## 確かめの回し方

上の表で確かめがかかるブランチは、照合と同じとき（PR を出す前と、PR に push する前）に、アプリを動かして触れた機能を確かめる。サーバーは `verify-server` スキル（`.agents/skills/verify-server/`）で、アプリは `verify-ios` スキル（`.agents/skills/verify-ios/`、Mac のセッションだけ）で確かめる。

1. 差分から、触れた機能を地図の索引（`.agents/skills/verify-<アプリ>/features/README.md`）で引く
2. その機能のファイルにある入口をすべて通す
3. 機能を足した、入口や見え方を変えたときは、同じ PR で地図を直す（機能のファイルの形は `.agents/skills/verify-<アプリ>/MAP-FORMAT.md`）
4. PR の本文の `## 確かめ` に、機能と入口ごとに、した操作と見えた結果と、確かめたコミットを書く。UI テストの全件の回がかかる PR で書くものは `ios/AGENTS.md` の「確かめる」
5. 動かせない入口は「確かめていない」と書き、どこで確かめるかを書く。確かめる場所は、各 `verify-<アプリ>` スキルの「確かめられないとき」にある

main や前のブランチを取り込んだだけの push と、`/implement-spec` の draft PR にチケットを取り込む push では回さない（下の「`/implement-spec` の draft PR」）。

**Why:** テストと好みのレビューが通っても、本物の経路で機能が動くかは、merge のあとの `main-flow-on-development` まで分からなかった。`/implement` の中だけに置くと、`/diagnosing-bugs` からの直しや小さな直しが通らないので、PR のゲートに置いた（#902）。

### 端末とサーバーをつなぐ確かめ

API の境目にかかる変更は、PR を出す前に、Mac のセッションで、シミュレーターのアプリを手元のサーバーにつないで入口を通す。回し方は `verify-ios` の「手元のサーバーにつないで動かす」。

API の境目にかかる変更は、次のどれかを変える差分にする。サーバーと iOS のどちら側の差分でも当たる。

- 同期: `/v1/sync/*` の受け口、端末の送り待ち、サーバーの帳簿
- 記録の種類の足し引き
- 境目をまたぐ値の書き方: ID・日時・数
- API のスキーマ: `server/openapi.json`
- 境目のどちら側に置くかを組み直すリファクタ

1. 通す入口は、差分が触れた記録の種類の、書き込み → 帳簿に入る → 端末の置き場を空にして開き直す → 取りに行って画面に戻る、と、取りに行った記録を直して送り返す道。触れた種類を画面から書けないときは、体重で通す
2. PR の本文の `## 確かめ` に、通した入口と、画面で見えた要素と、帳簿に入った記録（種類と ID と `version`）と、確かめたコミットを書く
3. クラウドのセッションでは回せない。PR は止めず、`## 確かめ` に「端末とサーバーをつなぐ確かめは、クラウドのセッションなので確かめていない」と書き、サーバーの側を `verify-server` で、アプリの側を偽の同期サーバーの場面で確かめた結果を書く（`verify-ios` の「確かめられないとき」）

PR のゲートの条件にも CI にも置かない。merge の条件にもしない。

**Why:** 型の照合では見えない値の書き方の食い違い（#362 の大文字の ID）は、端末とサーバーをつないで初めて見え、それまでは merge のあとの TestFlight の版まで分からなかった。Mac でしか回らないので、ゲートに置くとクラウドのセッションの PR が止まる。CI に置くには UI テストをサーバーにつなぐことになり、`ios/AGENTS.md` の決まりを変える別の決定になる（#1002）。

## `/implement-spec` の draft PR

`/implement-spec` の統合ブランチの draft PR では、チケットを取り込むたびの push に照合と確かめをかけない（`scripts/check` と CI は通る）。

1. 全チケットを取り込んだら、draft を ready にする前に、チケットごとでなく統合の差分の全体（`origin/main...HEAD`）に、上の表でかかる照合と確かめを通す。かかるなら上の「敵役の試し」を、照合の前に1回回す。照合は上の「照合の回し方」の周で、仕様の照合は上の「仕様の照合」のとおりに回す
2. ready にしたあとは、ほかの PR と同じく push ごとにかける

`mac` のチケット（`docs/agents/issue-tracker.md` の「iOS のチケットの分け方」）で通した入口は、確かめたコミットのあとにその入口が通るファイルを触っていなければ、1で回し直さない。`## 確かめ` に、その入口を確かめたチケットの番号とコミットを書いて証拠に指す。触っていたら回し直す。1の時点で `mac` のチケットが終わっていなければ（クラウドの統括では `mac` のチケットを拾わない）、その入口は「確かめていない」と書いて確かめる場所にそのチケットを指し、チケットが閉じたら証拠に書き換える。統合の PR を `mac` のチケットが閉じるまで merge しないのは、`docs/agents/issue-tracker.md` の「iOS のチケットの分け方」のとおり。

**Why:** 取り込みのたびに照らすと、あとのチケットで変わる差分を何度も照らし直すことになる（上の「照合の回し方」の Why）。`mac` のチケットはシミュレーターで入口を通すためのもので、同じ入口をゲートでもう一度通すと二度手間になる（#989）。

## merge のあとに気づくもの

- `deploy.yml`: 開発用に出した Worker の `/health` と、開発用の環境で主な流れを通す `main-flow-on-development`。`main-flow-on-development` が main で落ちたら Issue が立つ（`docs/agents/tooling.md` の「CI」）
- `ios-ui-test.yml`: main への push で UI テストの全件を回し、落ちたテストごとに Issue が立つ（`docs/agents/tooling.md` の「CI」）
- 本番の Sentry の課題が Issue になる（`docs/agents/tooling.md` の「本番の知らせを Issue にする」）
- 実機の確認: ヘルスケア・カメラ・通知・写真の読み込みに触れた PR は、merge のあとに人が確かめる（`docs/agents/ios-release.md` の「実機の確認」）
- 週1回の地図の見回り: 検証スキルの地図を、定期のタスクが見直す（`docs/agents/tooling.md` の「検証スキルの地図の見回り」）

## 知られている漏れ

- 端末とサーバーのつなぎは、API の境目にかかる変更に Mac のセッションでだけ確かめる（上の「端末とサーバーをつなぐ確かめ」）。クラウドのセッションの PR と、API の境目にかからない変更では、merge のあとの TestFlight の版まで確かめない。`main-flow-on-development` はサーバーの API を叩くだけでアプリを動かさず、敵役の試しもサーバーの範囲だけを走らせるので、端末の送り方に因る不具合（#362）はそこでも見つからない
- `site/` には動かす確かめが無い
