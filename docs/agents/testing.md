# テストの好み

テストを書く・直すときに従う。テストもコードなので `docs/agents/coding-style.md` も当てる。言語ごとの当てはめは `docs/agents/languages/<言語>.md` にあり、そこで置き換えると書いた箇所はそちらに従う。

## テストの粒度

- テストも保守するものなので、数は最小限にする
- 統合テスト（テスト対象を、実際に組み合わせて使うものと一緒に動かすテスト）を基本にする。単体テストは、状態管理が複雑なときと、分岐が多いときだけ書く
- 宣言したことをフレームワークが保証する挙動（永続化のスキーマで宣言した既定値や制約など）は、アプリのテストで確かめ直さない。宣言と二重に管理することになる

## ロジックと UI の分担

- 純粋な関数の分岐の網羅は、単体テストで行う
- UI テストは、画面の経路と状態の移り変わりに絞る（入力欄から体重を記録する → タイムラインに体重記録が出る、シートを閉じる → 元の場所にフォーカスが戻る、など）
- 同じ分岐は、単体テストか UI テストのどちらか一方で確かめる。文言や属性の確認を単体テストで済ませたら、UI テストからは外す

## テストの構造

- テストのまとまりを「機能 → シナリオの分類」の順に入れ子にし、個々のテストに具体的な振る舞いを書く。分類の中で条件が違うときは、条件ごとのまとまりを足す
- まとまりとテストの名前は日本語で書く。条件はまとまりの名前に書き、テストは「〜こと」の形で振る舞いを書く
- 入力と準備（テスト用の依存、データ、状態）は、その条件のまとまりの「各テストの前の準備」で作る。使うテストが1つでも、ここに置く（`docs/agents/coding-style.md` の「定数は最小のスコープに置く」より、こちらを優先する）
- テストの本体は、振る舞いの実行と検証だけにする
- 既定では、ケースを表にして1つのテストで回す書き方（パラメータ化テスト）にせず、条件を名前にしたまとまりと、個別のテストをベタ書きする。行数が増えても、読みやすさを取る
- パラメータ化テストは、それが要り、ほかの書き方より合うときだけ使う（例: ルートの `AGENTS.md` の「端末とサーバーの両方に置く決めごと」のテスト）。このときは、ケースに条件の名前を持たせ、テストの名前に使う

**Why:** 条件をまとまりの名前に、期待をテストに書くと、読むときに表と本体を行き来せずに済み、テストを足すときはテストを1つ足すだけになる。

## 依存の差し替え

- テスト対象が使う依存（別の型や関数）を差し替えるときは、差し替え用のものを別のファイルに作る
- テスト対象に渡すコールバックは、テストの中でその場で書く
- 差し替え用のものは、成功と失敗で別の作り方を用意する。名前は ok と error を対にする
  - 成功: 既定のデータを持ち、引数で一部を上書きできる
  - 失敗: 具体的なエラーの型を受け取る
- 差し替え用のものは呼び出しを記録し、テストで引数を確かめられるようにする。引数を確かめるテストは、まとまりの準備で作ったものを持って参照し、結果だけを確かめるテストはテスト対象に渡すだけにする

## ファイルの置き場所

- テストは、実装と対応する場所に、テスト対象の名前を元にした名前で置く
- 差し替え用のものは、差し替える依存の名前を元にした名前にする

## 日時は実行環境に左右されない形で確かめる

CI のランナーはタイムゾーンが UTC、ロケールが英語のことが多く、手元は日本時間・日本語のことが多い。日時の整形は、指定しなければ実行環境のタイムゾーンとロケールに従うので、その結果を期待値に直書きしたテストは、手元で通っても CI で落ちる。

日時を含む検証は、次のどれかにする。

- 時刻を含まない部分で照合する
- 値が等しい・異なるという関係を確かめる
- テストの中で同じ設定で整形して比べる

疑わしいときは、タイムゾーンとロケールを変えても通ることを確かめる。
