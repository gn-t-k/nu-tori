# テストの好み

テストを書く・直すときに従う。テストもコードなので `docs/agents/coding-style.md` も当てる。

## テストの粒度

- テストも保守するものなので、数は最小限にする
- 統合テスト（Swift Testing で、テスト対象を実際に組み合わせて使う型と一緒に動かすテスト）を基本にする。単体テストは、状態管理が複雑なときと、分岐が多いときだけ書く
- 宣言したことをフレームワークが保証する挙動（永続化のスキーマで宣言した既定値や制約など）は、アプリのテストで確かめ直さない。宣言と二重に管理することになる

## ロジックと UI の分担

- 純粋な関数の分岐の網羅は、単体テスト（Swift Testing）で行う
- UI テスト（XCUITest）は、画面の経路と状態の移り変わりに絞る（入力欄から体重を記録する → タイムラインに体重記録が出る、シートを閉じる → 元の場所にフォーカスが戻る、など）
- 同じ分岐は、単体テストか UI テストのどちらか一方で確かめる。文言や属性の確認を単体テストで済ませたら、UI テストからは外す

## テストの構造

UI テスト以外は Swift Testing で書く。

- `@Suite` を「機能 → シナリオの分類」の順に入れ子にし、`@Test` に具体的な振る舞いを書く。分類の中で条件が違うときは、条件ごとの `@Suite` を足す
- 表示名は日本語で書く。`@Test` は「〜こと」の形で振る舞いを書き、条件は `@Suite` の名前に書く
- 入力と準備（テスト用の依存、データ、状態）は、その条件の `@Suite` の `init()` で作る。使う `@Test` が1つでも、ここに置く（`docs/agents/coding-style.md` の「定数は最小のスコープに置く」より、こちらを優先する）。Swift Testing は `@Test` ごとに Suite を作り直すので、`init()` が各テストの前の準備になる
- `@Test` の本体は、振る舞いの実行と検証だけにする
- ケースを `@Test(arguments:)` で並べず、条件を名前にした `@Suite` と、個別の `@Test` で書く

```swift
@Suite("体重の傾向の計算")
struct ComputeWeightTrendTests {
    @Suite("体重記録が1件もないとき")
    struct NoRecords {
        let records: [WeightRecord]

        init() {
            records = []
        }

        @Test("傾向が空になること")
        func trendIsEmpty() {
            #expect(computeWeightTrend(from: records).isEmpty)
        }
    }
}
```

UI テストは XCTestCase で、同じ並びにする。条件ごとに1つのクラスを1つのファイルに置き、クラス名とファイル名に経路と条件を書く（`RecordWeightWithoutGoalUITests.swift`）。準備（アプリの起動と、条件の状態にするまでの操作）は `setUp` で行い、メソッドは `test_〜こと` の名前で振る舞いの実行と検証だけにする。

**Why:** 条件をまとまりの名前に、期待をテストに書くと、テストを足すときはテストを1つ足すだけになる。

## 依存の差し替え

- テスト対象が使う依存（別の型や関数）を差し替えるときは、差し替え用の型をテストターゲットに作る
- テスト対象に渡すコールバックは、テストの中でクロージャを書く
- 差し替え用の型は `{依存の名前}Mock` とし（`WeightRecordStore` → `WeightRecordStoreMock`）、成功と失敗で別の作り方を、その型の static 関数として用意する
  - 成功: `.ok(...)`。既定のデータを持ち、引数で一部を上書きできる
  - 失敗: `.error(_:)`。具体的なエラーの型を受け取る
- 差し替え用の型は class にして呼び出しを記録し、テストで引数を確かめられるようにする。引数を確かめるテストは Suite のプロパティに持って `@Test` で参照し、結果だけを確かめるテストはテスト対象に渡すだけにする

## ファイルの置き場所

- Swift Testing のテスト: テストターゲットの中で実装と同じディレクトリ構成にし、`{テスト対象の名前}Tests.swift` にする（`computeWeightTrend` → `ComputeWeightTrendTests.swift`）
- 差し替え用の型: テストターゲットに `{依存の名前}Mock.swift` で置く

## 日時は実行環境に左右されない形で確かめる

GitHub Actions の macOS のランナーはタイムゾーンが UTC、ロケールが英語で、手元は日本時間・日本語のことが多い。`Date.formatted()` や `FormatStyle` は、指定しなければ実行環境のタイムゾーンとロケールで整形するので、その結果を期待値に直書きしたテストは、手元で通っても CI で落ちる。

日時を含む検証は、次のどれかにする。

- 時刻を含まない部分で照合する
- 値が等しい・異なるという関係を確かめる
- テストの中で同じ設定で整形して比べる

疑わしいときは、`TEST_RUNNER_TZ=UTC xcodebuild test -testLanguage en -testRegion US ...` のようにタイムゾーンとロケールを変えても通ることを確かめる。UI テストで起動するアプリには `TEST_RUNNER_TZ` が届かないので、`XCUIApplication` の `launchEnvironment` で `TZ` を渡す。
