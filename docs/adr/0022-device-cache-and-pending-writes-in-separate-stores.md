# 端末のキャッシュと送り待ちは別の置き場に持ち、送り待ちを先に保存する

端末の SwiftData を、キャッシュ（記録、通し番号、読めた種類）の置き場と、送り待ち（とヘルスケアの同期の進み具合）の置き場の2つに分ける。記録を作る・直すときは、送り待ちを先に保存し、キャッシュをそのあとに保存する。ADR-0013 の「端末で作ったものや直したものは、それを保存するのと同じ保存の中で、送り待ちの列に1件足す」を、これで置き換える。

1つの置き場のままだと、キャッシュのモデルの形を変えたときに、移行できない形として置き場ごと退避され、送り待ちも一緒に消えうる。キャッシュはサーバーの写しでいつ捨てても取り直せるので、キャッシュの置き場は移行を持たず、形が合わなければ消して全部取り直す。移行で守るのは送り待ちの置き場だけになり、記録の種類を足すたびに版を足す必要も無くなる。

保存を2つに分けると、途中で落ちたときに片方だけが残りうる。送り待ちを先にすれば、残る形は「送り待ちはあるが、キャッシュに無い」だけで、送って取りに行けばそろう。逆の「キャッシュにはあるが、送り待ちに無い」（送り忘れ）は起きない。

## 検討した案

- 1つの置き場のまま、版ごとにモデルの写しを固める（Apple の勧める形）: 保存は1回で済む。記録の種類を足すたびに版を足し、並べたチケットがそれぞれ同じ次の版を作ってぶつかる。main に入るたびに TestFlight に配られるので、同じ版の番号で違う形を2度出す危険も残る
- 2つの置き場にまたがる1回の保存に頼る: 別のファイルのあいだの保存が1つになるかを確かめられず、落ちたときの形が決まらない

## 起きること

- 送り待ちを保存したあと、キャッシュを保存する前に落ちると、作った記録が次に取りに行くまでタイムラインに出ない
- キャッシュの形が変わった版に上げると、最初に開いたときに全部取り直す。取り終えるまでタイムラインは読み込み中になる
