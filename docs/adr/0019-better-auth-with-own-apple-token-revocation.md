# 認証は Better Auth に任せ、Apple のトークンの交換と取り消しだけを自分で書く

サーバーの認証（Apple の ID トークンの検証、セッションの発行・延長・取り消し）は、Better Auth に任せる。開発者は認証そのものに関心を割かず、保守するコードを減らしたい。形も、自分たちで考えたものより、多くの人が使うライブラリの既定に乗るほうが信頼できる。Better Auth の表は D1 の中の認証の置き場に閉じ、ほかの表と Durable Object はアカウント ID だけを見るので、表の形がライブラリのものでもほかに漏れない。

Better Auth は、ネイティブの ID トークンの流れで認可コードを受けず、Apple のリフレッシュトークンを持たず、削除のときに Apple のトークンを取り消さない。App Store はアカウントの削除で取り消すことを求めるので、コードの交換、リフレッシュトークンの暗号化した保存、削除のときの取り消しだけは自分で書く。

## 検討した案

- jose と D1 で手で書く: 依存が jose と Hono だけで、nonce をサーバーが出した値で縛る、セッションのトークンをハッシュで置くといった厳しめの形をそのまま書ける。Better Auth でも Apple のトークンの交換と取り消しは自分で書くので、任せられるのは ID トークンの検証とセッションで、差は数百行ほど。それでも、保守するコードを増やさないことを選んだ
- 外部の認証サービス（Supabase Auth、Firebase Auth、Clerk、Auth0）: ユーザー ID とセッションがサービスのものになり、使わない期間で延びるセッションの形と合わない。Apple のトークンの交換と取り消しまでするのは Auth0 だけ
- Lucia、Auth.js、OpenAuth: Lucia は非推奨で見本のコードだけが残る。Auth.js と OpenAuth は、ネイティブの ID トークンを受ける口が無い

## 起きること

- nonce は端末が作り、Better Auth がトークンの中の値と比べるだけ。サーバーが出した値で縛らない
- セッションのトークンは D1 にそのまま入る（D1 は保存時に Cloudflare の鍵で暗号化される）
- Better Auth がメールを必須にするので、Apple のメールは保存せず、仮の値を入れる
- Apple の公開鍵を検証のたびに取りに行くので、Apple の応答が遅いとサインインが遅れる
- 版を上げる作業が続く。1.x の中でも中核の表の変更が一度入って戻されたので、上げるときは変更履歴の表の変更を確かめる
- Workers と D1 でネイティブの ID トークンの流れが通ることは、まだ動かして確かめていない。通らなければ jose と D1 で手で書く

今の決定は、`server/AGENTS.md` の「認証と不正利用防止」と、`ios/AGENTS.md` の「同期」のサインインにある。調べた事実は `docs/research/server-auth-library.md` にある。
