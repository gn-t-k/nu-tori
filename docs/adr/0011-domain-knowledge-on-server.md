# ドメイン知識の正本はサーバーに置き、端末には不利益を避けるためのものだけを置く

ドメイン知識（計算・判定・検証の決めごと。推定消費量の式、栄養の合計の数え方、日と週の区切り、目標に届いたかの判定、体重として受け付ける値の範囲など）の正本は1か所にし、既定はサーバーの TypeScript のドメイン層にする。記録の正本もサーバーにある（ADR-0008）ので、知識と記録の置き場がそろい、直すときは1か所で済む。見た目の決めごと（`DESIGN.md`）と、ヘルスケアとの対応づけのような端末の入出力の変換は、ドメイン知識に含めない。

端末に置くのは、サーバーに置くと次のどれかでユーザーが不利益を被るものだけにする。「端末で計算したほうが実装が楽」「サーバーの負荷が減る」は理由にしない。

1. 電波がないと、自分の操作の結果が見えない
2. 操作についてくる速さが要る（サーバーとの往復の遅れが見える）
3. アプリが開かれていないとき、または電波がないときにも動く必要がある

端末に置いたもののうち、サーバーも同じ結果を出す必要があるもの（栄養の合計の数え方、日と週の区切り、受け付ける値の範囲）だけは、両側に置く。係数や範囲のような数値はデータにしてリポジトリの1か所に置き、両側で読む。手順は Swift と TypeScript の両方に書き、入力と期待値の JSON をリポジトリの1か所に置いて、両方のテストで読む。端末とサーバーで値や検証の結果が違ったときは、サーバーを正とする。両側に要る知識が、小さな純粋な計算の域を超えたら、TypeScript で1回だけ書き、端末では JavaScriptCore で同じ JS を動かす形に移る。

この基準で ADR-0009 の端末の一覧を見直し、いつもの時刻の学習をサーバーに移した。端末に要るのは、学習の結果を受け取ってローカル通知を予約し、取り消すことだけだった（基準3）。あわせて、記録忘れの判定（基準3）と入力の検証（基準2）を端末に置くものとして挙げ、料理の量を直したときの材料の量の比例は端末だけが持つことにした（サーバーは比例させた結果を保存する）。

## 検討した案

- 両側に要る知識を、最初から TypeScript で1回だけ書き、端末では JavaScriptCore で動かす: 本当に1か所になるが、TS を JS にしてアプリに入れる手順、Swift と JS の境界の型、Swift 6 の並行性の中での扱いが増え、境界のテストは Mac が要る。両側に要るのが足し算と区切りのような小さな計算のうちは、見合わない
- サーバーを Swift で書き、端末と同じコードを使う: 両側に要る知識は小さく、開発者の専門（TypeScript）と LLM の SDK の揃い方を捨てるほどではない

## 起きること

- 電波がないときに記録した体重は、同期するまでいつもの時刻の学習に入らない。その体重で目標に届いても、「目標に届いた」の知らせは同期するまで出ない。記録そのものはすぐ見える
