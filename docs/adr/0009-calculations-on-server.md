# 目標と目安の計算はサーバーで行い、身体データと過去の食事の栄養は送るが保存しない

体重の傾向、推定消費量、1日の目安、目標案、大変さ、目標までのペース、目標に届いたかの判定は、サーバーで計算する。推定消費量の手法はリリース後に調整する見込みが高く、サーバーなら App Store の審査を待たずに直せる（ADR-0004 で OTA 更新がないことへの手当て）。目標と目安の式を1か所にまとめる。いつもの時刻の学習（ローカル通知の時刻に使う）もサーバーで行い、端末は学習の結果を受け取って通知を予約する。端末で計算するのは、記録をまとめて見せるための計算（材料から料理・食事への栄養の合計、料理の量を直したときの材料の量の比例、1日の丸・日のまとめの合計、週の振り返りの平均、習慣トラッカー）だけにする。これらは直した値がオフラインでもすぐ見えるようにするため端末に置く（端末に置く基準は ADR-0011）。料理の量を直したときの材料の量の比例は端末だけが持ち、端末は比例させた結果をサーバーに送る。サーバーも推定消費量と AI の発言の文脈のために栄養の合計を出すので、合計の決めごと（kcal の数え方など）は端末とサーバーで同じものを使う（両側への置き方は ADR-0011）。

目標案と最初の推定消費量は、身体データとヘルスケアの過去の食事の栄養から出すので、これらはサーバーに送る。生年月日は端末が日付から年齢にして送る。サーバーは計算に使ったら捨て、DB にもログにも残さない。身体データを持ち続けないことは、送っても保存しないことで守る。

## 検討した案

- すべて端末（Swift）で計算する: オフラインでも目標を立てられ、身体データが端末を出ない。式を直すたびにアプリの審査が要る
- 目標案と最初の見積もりは端末、週ごとの見直しはサーバー: 同じ種類の計算が2つの言語に分かれ、ずれやすい

## 起きること

- 目標を立てるときと、期限と目標体重を自分で入れて大変さを見るときは、電波が要る
- 日と週の区切り（ADR-0006）で計算するので、サーバーはユーザーのタイムゾーンを持つ
- 電波がないときに記録した体重は、同期するまで体重の傾向に入らない
