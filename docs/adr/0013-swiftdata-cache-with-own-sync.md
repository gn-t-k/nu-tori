# 端末のキャッシュは SwiftData に持ち、サーバーとの同期は自前で書く

端末のキャッシュは SwiftData に持ち、iOS の最低対応版は 27 にする。同期は既製の仕組みを使わず、自前で書く。

- ID はすべて UUID にする。端末で作るものの ID は端末で振る（v4）。どの端末で作っても同じになってほしいもの（端末で出す知らせ、ヘルスケアから取り込んだ体重記録）は、名前から決まる v5 にし、2台の端末や入れ直しでも重ならないようにする。サーバーが作るものは v4
- 端末で作ったものや直したものは、それを保存するのと同じ保存の中で、送り待ちの列に1件足す
- 送り待ちは順に送る。サーバーは書き込みごとの ID で重複を除き、同じ書き込みが何度届いても結果が変わらないようにする（冪等）
- 競合を判断する単位は、食事、料理、材料、体重記録、目標、知らせのそれぞれ1つにする。競合したら、サーバーがあとに受け取ったほうを採る（端末の時計には頼らない）
- 片方で消し、もう片方で直したときは、削除を採る
- 端末は、アカウントごとの変更の通し番号を使い、前回の続きからの変更を取りに行く。消したものは、削除の印として受け取る

こうすると、電波がないときも、目標の設定、アカウントの削除、サインインのほかはいつもどおりに操作でき、記録や直しがすぐ見える（ADR-0001 の1位・6位）。扱うものの種類は少なく、1人の記録なので、競合の規則は小さく済む。

SwiftData については、サーバーを正本にしたキャッシュの作り方を Apple がサンプルで示している。ただしこのサンプルは、端末から書き戻さない読み取り専用のキャッシュで、書き戻す部分（送り待ちと送信）が自前で書くところになる。`@Query` とバックグラウンドの書き込みがデッドロックすることがある不具合が iOS 27 で直った（iOS 26 ではありうる）。初回リリースの利用者は開発者と身近な人から始まるので、iOS 27 に絞っても困らない。

## 検討した案

- PowerSync: Swift の SDK は正式版で、送り待ちの列も持つ。一方で、次の点が重い
  - サーバーに Postgres などの DB と PowerSync Service が要る。PowerSync Cloud は月 49 ドルからで、無料枠は1週間使わないと止まる。自前で動かす版は無料だが、PowerSync Service を自分で動かすことになる
  - 写真の添付の補助はまだ Alpha
  - SwiftData とは別のストアになる
- GRDB・SQLiteData: SQL で直接書け、SwiftData の不具合に縛られず iOS 26 にも対応できる。ただし独自のサーバーとの同期は GRDB でも自前になり、Linux 対応も公式には保守されていないので、ロジックを値型に分ける形は SwiftData と変わらない。Apple の外の依存を増やさないほうを取った
- 最低対応版を iOS 26 にする: 使える iPhone は広がるが、SwiftData の上の不具合を抱える
- ID をサーバーの連番にする: 電波がないと振れない。UUID v7（時刻順）は索引の効率がよいが、記録はアカウントごとの小さな DB に入るので利点が出ず、Foundation の `UUID()` では作れない。ULID は Swift に標準が無い

## 起きること

- iOS 26 のままの iPhone では使えない
- 2台目で直したあとに、1台目が電波のないあいだに直した古い分を送ると、古いほうが勝つ。2台を並べて使うときだけに起きるので受け入れる
- SwiftData は Linux で動かない。送り待ちの判断と、記録をまとめて見せるための計算は、SwiftData の型に触れない値型のロジックに分ける
- サーバーの API は、上の冪等な書き込み、変更の通し番号、削除の印を前提に作ることになる
- サーバーが書いたもの（写真からの推定の結果、AI の発言など）も、同じ変更の通し番号で端末に届く。プッシュは使わない
- 写真の送信も、既製の添付の仕組みを使わず自前で書く
