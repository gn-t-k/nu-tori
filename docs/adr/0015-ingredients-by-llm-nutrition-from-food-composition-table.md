# 写真から材料と量までを LLM が出し、栄養は成分表から引く

写真からの推定では、LLM が写真から「料理 → 材料 → 量」と、材料ごとに成分表を引くための語を返す。サーバーが成分表から材料ごとに候補を探し、文字だけの2回目の呼び出しで、LLM が候補から食品番号を選ぶ。栄養は、選んだ食品の値に量を掛けて出す。材料の栄養の出どころは、写真に栄養成分表示が写っていればその表示、無ければ成分表、成分表に合うものも無ければ LLM の推定の順に決める。LLM が推定するのは、エネルギー・たんぱく質・脂質・炭水化物・食物繊維・食塩相当量までにする。ミネラルとビタミンは「不明」にする。

LLM に栄養の数値まで出させると、根拠を辿れず、同じ写真でも値がばらつく。ビタミンやミネラルは、それらしい数字が出て誤解を招く。成分表を引く工程を分ければ、材料ごとに食品番号と栄養の出どころを持てるので、当て方をあとから直せる。

## 検討した案

- 一段（LLM が写真から栄養まで返す）: 呼び出しは1回で済むが、根拠を辿れない。`docs/ui-design/0001-first-release/index.md` の「出荷後の検証」で比べるため、サーバーに評価用の経路としてだけ持ち、アプリからは呼ばない
- 成分表の 2,538 食品の名前をプロンプトに丸ごと入れ、1回で食品番号まで返させる: 呼び出しごとに数万トークンのキャッシュ読みがかかる。長い一覧から選び間違えたとき、原因を追いにくい
- 料理 → 材料 → 成分表の三段: 写真を2回送るので、費用と待ち時間が増える
- LLM に栄養を推定させず、成分表でいちばん近い食品で代用する: 市販品やチェーン店のメニューで、主原料や調理法の違う食品の値を流用することになる

## 起きること

- 写真を送るのは1回だけで、成分表を引く2回目は文字だけで済む
- 材料は、量（g）、成分表の食品番号（成分表から引いたとき）、栄養の出どころ（表示・成分表・AI の推定）を持つ
- 出どころが LLM の推定の材料を含む料理では、栄養の内訳のミネラルとビタミンに「不明」が混じる。成分表の未測定（「-」）も、0 ではなく「不明」として扱う
- 栄養成分表示は、写っていたときだけ使う。裏の表示を撮るようユーザーに頼まない（ADR-0001、ADR-0002）
