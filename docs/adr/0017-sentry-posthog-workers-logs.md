# 失敗は Sentry、行動と分析は PostHog、要求のログは Workers Logs に分ける

出荷後の観測を3つの道具に分ける。失敗の知らせとデバッグ（端末のクラッシュと対処した失敗、サーバーの例外）は Sentry、ユーザーの行動と、サーバーだけが知るドメインの信号（推定のトークンとやり直し、量の修正の率、週ごとの見直しの旗、同期の送り待ち）の分析は PostHog、要求ごとの細かいログは Cloudflare の Workers Logs に置く。どれにも記録の中身を送らず、PostHog に送る数値は数・率・差・旗だけにする。Sentry と PostHog はどちらも EU に置く。

Cloudflare には Workers のエラー率の通知が無く（Enterprise のゾーン向けだけ）、一人で運用するには「壊れたらすぐ気づく」を別の道具に任せる必要がある。Sentry は無料のプランでも、新しい issue・急増・回帰をメールで知らせ、Swift のクラッシュのメッセージも残る。一方、ファネルや継続率の画面を自前で作って保守するのは割に合わないので、分析は PostHog に任せる。Durable Object の記録は全員をまたいで問い合わせられないので、サーバーが記録を書くときに出来事を PostHog に送り、分析の置き場を1つにする。

## 検討した案

- PostHog に一本化する（エラートラッキングも PostHog）: 第三者が1つで済み、人ごとに消せる。Swift のクラッシュのメッセージが残らず、issue の通知はメールで受けられない
- 行動分析は入れず、ドメインの信号だけを自前（Workers Analytics Engine か D1）に置く: 第三者が増えない。Analytics Engine は行を消せず（保持 3 か月）、D1 は1つの DB に全員の書き込みが集まる。集計の画面を自前で作ることになる
- 行動の出来事を種類と日時だけに絞ってサーバーで作る: 端末に SDK が要らない。デバッグにも行動分析にも細かさが足りない

## 起きること

- 第三者が2つ増え、プライバシーポリシーの送り先、App Privacy の申告、アカウントの削除のときに消す先がそれぞれ増える
- Sentry は1人の分を消す手段が無いので、アカウントを消しても、Sentry に送った失敗の報告は保持期間（ふだんは 30 日）まで残る。PostHog は消す API を呼ぶが、消えるのは非同期
- データの置き場（EU）は、どちらもあとから移せない
- 利用者が少ないうちは、PostHog の継続率やファネルの数字はほとんど何も言わない。直接聞くことが主になる
