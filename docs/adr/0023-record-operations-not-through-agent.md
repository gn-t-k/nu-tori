# 記録の操作はエージェントを通さない

記録（食事、料理、材料、体重記録など）を作る・直す・消す操作は、今のまま端末とサーバーの同期で行う（ADR-0013）。記録の API を MCP（LLM が外のツールを呼ぶための決まった形）にして、端末が LLM のエージェント（どのツールをいつ呼ぶかを自分で決める LLM）とだけやりとりする形にはしない。会話の中で AI が記録の直し方を示すときも、AI は記録を直接直さない。ユーザーが直し方のボタンを押したときに、端末が、ユーザーが自分で直したときと同じ書き込みを作り、送り待ちに入れる。

電波が悪いときに、操作できなかったり遅くなったりして、ユーザーをいらだたせないためである。記録の操作が LLM の1ターンを待つ形は、これに反する。

また、仕様を詰める壁打ちで多かった同期の問いは、次の4つから生まれていた。

- 電波がないときにも記録できること
- 推定を待つあいだに直せること
- 複数の端末
- ヘルスケアとの読み書き

この4つは、どれもエージェントの形にしても残る。サーバーが LLM とタイミングを握ること自体から来る問いは一部で、そのほとんどは限界として受け入れて済んでいた。

## 検討した案

- 端末はエージェントとだけ話し、エージェントが MCP で記録を扱う: 体重を入れる・料理の名前を直すたびに LLM を待ち、電波が悪いと止まる。電波がないときのための送り待ちを残すなら、同期の仕組みも減らない。決めごとがドメイン層からプロンプトに移り、ADR-0011 とぶつかる
- 端末は今のまま、サーバーの中で推定の段取りをエージェントに替える: 端末は変わらないが、アラームの予定、やり直し、推定の回数の上限は非同期で動かすかぎり残る。今の推定の仕組みを替える理由にはならない。会話のエージェントに推定や読み分けを持たせるかは、「[会話を、記録を調べてから答えるエージェントの形にするか](https://github.com/gn-t-k/nu-tori/issues/366)」で決める
- 会話の中で AI が記録を直接直す: サーバーの書き込みが、端末でまだ送れていない直しとぶつかり、同期の問いが戻る。操作の主導権もユーザーから離れる

## 起きること

- 同期の仕組み（送り待ち、キャッシュ、帳簿）はそのまま残る。問いを減らすのは、仕組みを替えることではなく、製品の側で割り切ることで行う。推定中の食事は、消すことだけできるようにすることにした（実装は「[推定中の食事は、消すことだけできるようにする](https://github.com/gn-t-k/nu-tori/issues/365)」）

## 再検討の条件

- 端末の中で動く LLM が、記録の操作を任せられるほど賢く、操作についてこられるほど速くなったとき。サーバーの LLM がいくら速くなっても、電波が悪ければ遅れる
- 記録の操作の多くを、アプリの外で（ChatGPT などから MCP で）行うようになったとき。MCP での公開は「[記録の API を MCP で公開し、ChatGPT などから使えるようにする](https://github.com/gn-t-k/nu-tori/issues/363)」

根拠: 「[同期を単純にするために、記録の操作をエージェントと MCP に移すか](https://github.com/gn-t-k/nu-tori/issues/364)」の解決コメント
