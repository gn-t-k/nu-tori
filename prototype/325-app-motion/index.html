nu-tori の動き

Issue #325「アプリ全体の動きを決める」の、動かす場所の洗い出しをやり直した試作です。今回は emilkowalski/skills を実際に入れたブランチで、ask-emil が勧める道筋に沿って進めました。

ask-emil「足りない動きを探す」→find-animation-opportunities→候補7・見送り5→prototype→review-animations（この試作に当てた）

各場面の「▶ 再生」で、左の「今」（今の main のコード）と右の「案」を同時に動かします。案の動きは SwiftUI のばね（.smooth(duration:) と .spring(duration:bounce:)）を同じ式で計算して再現しているので、実機でもほぼこの速さと減速になります。

スローは、重なりや順番を目で追うためのもの。視差効果を減らすがオンのときは、拡大と移動をやめて薄れるだけにします。

動かす候補

見る頻度・動きの目的・速さの予算（0.3 秒前後）・読む情報を邪魔しないか、の4つの関門を全部通ったものだけです。効き目の大きい順に並べました。

今
案

振り付け

もの役始まり動き
決まったカード主0ms96% から、少し弾む
設定のカード添え0ms薄れて抜ける

弾み（bounce）を使うのはここだけです。何か月かに1回の、気持ちが動く場面なので、喜びの予算をここに使います。ほかの場面は弾ませません。

SwiftUI

// GoalSetupNoticeCard
GoalDecidedCard(…)
  .transition(.opacity
    .combined(with: .scale(scale: 0.96)))
.animation(.spring(duration: 0.4, bounce: 0.15),
           value: form)
.sensoryFeedback(.success, trigger: form) { _, new in
  new == .decided }

動かさない場所

  • 帯の週送り・日を押す・タイムラインのさかのぼり（DayRingStrip.swift:14、TimelineViewport）。1日に何十回も触る。週送りはシステムのページ送りのままにする。
  • グラフの描き出し（体重の傾向・週の振り返り・目標の画面）。読むための数字。線が伸びる飾りは読むのを遅らせる。
  • 丸のボタンやカードを押したときの縮み（scale 0.97）。標準のボタンの押した表示がもうあり、独自の振る舞いは足さない（DESIGN.md の Do）。実機で押した表示が弱いと感じたら、そこで見直す。
  • 写真が読めたときのフェード（MealCardView.swift:125）。開くたびに全部のカードで起きる。端末にある写真は一瞬で出るので、薄れはかえって遅く見える。
  • 開いたときに届く新しい知らせ・週の振り返りのカード。開いた直後の同期で届き、見る前に動き終わるか、開くたびに動いて見える。

あわせて、もうある動きも見ました。届いていない記録の薄さ（UndeliveredRecordStyle.swift:13、0.25 秒）はこのままで良いです。目標の設定のページ送り（GoalSetupFlowCard.swift:28）は「戻る」でも右から入るので、向きが操作と逆になっています。これは足す動きでなく直す動きなので、別に直します。

結論

nu-tori はほぼ SwiftUI の標準の動き（潜る、シート、値の巻き取り）に任せていて、足りないのはタイムラインに記録が出入りする瞬間だけです。1〜4 は同じ1つの決まり（日の並びの id に .smooth(duration: 0.3〜0.35) を掛け、出入りするものに薄れと 97〜98% を付ける）で入るので、最初に当てるのは 1 と 2 が良いと考えます。5〜7 は小さく、あとで足せます。

前回の試作との違い: 前回は動きを CSS の決まった曲線（0.35 秒）で描いていて、SwiftUI のばねと減速が違いました。今回はばねを同じ式で再現しています。また前回は 1 を「同じ場所で入れ替わる」としていましたが、体重の行は記録した時刻の位置に出るので、あいだに食事があると別の場所に出ます（場面 1 の切り替えで見られます）。
