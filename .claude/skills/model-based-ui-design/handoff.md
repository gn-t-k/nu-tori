# 引き継ぎ：設計記録 → 正本

[SKILL.md](SKILL.md) の手順6。終盤ゲートを通った設計記録から、用語・決定・見た目を正本に移し、設計記録を凍結する。以後、現在の状態を知りたい人やエージェントは正本だけを読めばよい状態にするのが目的。出口は末尾の**引き継ぎゲート**。

各項目の書き込みは、変更内容をユーザーに示して承認を得てから行う。

---

## 1. 用語 → `CONTEXT.md`

`/domain-modeling` を起動し、その書式（CONTEXT-FORMAT）で登録する。

- `03-concept-model.md` の全概念オブジェクトについて、名前・1〜2文の定義・避ける同義語（③で作ったシソーラス）を登録する
- 既存の用語と名前や意味が変わるもの（再構築で多い）は、ユーザーにどちらを残すか確認してから書き換える
- 関連・多重度・属性は `CONTEXT.md` に書かない（用語集に徹する）。これらはコードのデータ構造に落ちる

## 2. 決定 → `docs/adr/`

`/domain-modeling` の ADR の書式（ADR-FORMAT）で、**1決定1ファイル**で書く。候補は次の通り。`/domain-modeling` の3条件（覆しにくい・文脈なしでは意外・本当にトレードオフがあった）をすべて満たすものだけを ADR にする:

| 候補 | 出どころ |
|---|---|
| 設計思想（トレードオフで何を取るか） | ④ |
| 最重要コンセプト | ④ |
| ナビの根（目標地点） | ⑤ |
| フォームファクタと、その判断に入った技術的事情 | ⑥ |
| モードの方針（モードレスを崩した箇所とその理由） | ⑦ |

- 各 ADR の本文に、根拠として設計記録の該当ファイルへのパスを書く（例: `docs/ui-design/0002-sharing/04-concept.md`）
- 既存の ADR を覆す決定は新しい ADR として書き、古い ADR の Status を `superseded by ADR-NNNN` にする。古い ADR の本文は書き換えない

## 3. 見た目とガードレール → `DESIGN.md`

リポジトリ直下の `DESIGN.md`（Google Labs の DESIGN.md 形式）に書き出す。書式は `npx @google/design.md spec` で最新の仕様を確認してから書く（形式が alpha のため）。

| DESIGN.md の見出し | 書き出し元 |
|---|---|
| Overview | ④の「提供したい体験」と「設計思想」の要約 |
| Colors / Typography / Elevation & Depth / Shapes | ⑦ルック&フィールのトークン |
| Layout | ⑥のうち、余白・グリッドの方針（ペイン構成やナビは書かない。コードと ADR が持つ） |
| Components | `07-components/` から取り出した部品（ボタン、チップ、リスト、入力欄など）と状態別の変種 |
| Do's and Don'ts | ⑥⑦のチェックポイントと、モードレスの原則 |

- 既存の `DESIGN.md` があれば、書き換え前の版を一時ファイルに退避して `npx @google/design.md diff <旧> DESIGN.md` で差分を出し、ユーザーに示す
- `npx @google/design.md lint DESIGN.md` のエラーを0件にする

## 4. 設計記録を凍結する

`index.md` の冒頭（見出しの直後）に次を書き、「引き継ぎ」節に更新した正本と ADR 番号を列挙する:

```markdown
> YYYY-MM-DD 時点の設計記録（凍結）。現在の用語・決定・見た目は `CONTEXT.md`・`docs/adr/`・`DESIGN.md`、構造はコードを見る。
```

以後この設計記録は書き換えない。変更が必要になったら新しい設計記録（機能追加・再構築）を作る。

## 5. 実装へ渡す

実装に進むなら、`/to-spec` に `index.md` の「実装はここから読む」を入力として渡す（`/to-tickets` → `/implement` と続く）。
