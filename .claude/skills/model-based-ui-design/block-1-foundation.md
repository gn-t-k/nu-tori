# 序盤ブロック：環境調査と基本設計（① ②）

[SKILL.md](SKILL.md) の序盤ブロック。用途と行動を整理する。①②は並行・反復してよい。出口は末尾の**序盤ゲート**。

## 入力

環境調査（ユーザーリサーチ）の成果物。

- **行動シナリオ** — ユーザーがその製品で取る具体的な行動を文章化したもの。`00-behavioral-scenarios.md` に保存。
- **ペルソナモデル** — 想定ユーザーの人物像（属性・文脈）を模型化したもの。ユースケースの〈誰〉に当てはめる具体人物（Aさん 等）。`00-persona-model.md` に保存。

揃え方: (a) ユーザーに既存の調査結果を求める。(b) 無ければユーザーと一緒に軽い環境調査（代表的な利用文脈と人物像の素描）を行う。素描でよいので、シナリオと人物像の実体を上記2ファイルに保存してから①に着手する（序盤ゲートはペルソナの実在を前提に判定するため）。

併用: 必要な情報が利用者や関係者の頭にあるなら、ユーザーに `/to-questionnaire` を起動して質問票を作ってもらう。競合や利用文脈の下調べは `/research` に任せる。

## ① ユースケース定義 → ユースケースモデル

ユーザーの用途を「**〈誰〉が〈何〉を〈行動〉できる**」構文で洗い出す。産出物は `01-use-cases.md`。

1. 行動シナリオから**名詞（オブジェクト）と動詞（タスク）**を抜き出す
2. 名詞を起点に「その製品でどう扱われるか」を連想し行動を広げる（レシピ → 読む / 投稿 / 検索）
3. ペルソナの**属性が違う人物**を〈誰〉に当てはめ用途を検討する
4. 構文に当てはめて一覧化する

併用: 叩き台を `/grilling` で問い詰め、抜けや断定形をつぶす。

**一覧の列**:

| 列 | 内容 |
|---|---|
| 動作主体〈誰〉 | ユーザー / システム / 具体ペルソナ |
| 対象物〈何〉 | 概念オブジェクトや UI コントロール（目的語） |
| 行動〈できる〉 | アクション。必ず可能形 |
| ユースケース名 | 構文から想定できる簡潔な名前（体言止め） |
| 分類 | 対象物軸 or 動作主体軸でグループ化 |
| 番号 | 分類名 + 連番。ゼロ埋めしない（例 `レシピ_1`, `レシピ_2`）。接頭辞は「分類」列で選んだ軸に揃える |

**チェックポイント**（括弧内はよくある罠）:
- すべてのユースケースが行動シナリオに由来し、「用途」を定義している（罠: 機能一覧化。粒度が曖昧で、ユーザー視点が薄いシステム都合の UI を生む）
- すべて可能形「〜できる」で書き、名前は体言止めにする。「しない」自由も含むので、モードレスな設計につながる（罠: 断定形「〜する」や「〜機能」という名前。達成必須と読めて設計コストが増え、モーダル化する）
- 漏れは序盤〜中盤のうちに加筆する（罠: 後半工程での加筆は手戻りが大きい）

## ② タスク整理 → タスク表

ユーザーの**アクション**とシステムの**働き**を CRUD で整理する。産出物は `02-tasks.md`。①と並行・反復してよい。

「タスク」には2種類ある: ユーザーがする**アクション**と、システムがする**機能（働き）**。さらに機能は粒度で2段に分ける:

- **特徴（Feature）** — 大きな括りの機能。1つのユースケースに対応する規模。
- **働き（Function）** — それを実現する小さな単位。1つの特徴（≒ユースケース）に複数の働きがぶら下がる。

「機能」という語は日本語では粒度が曖昧になるため、必ず Feature / Function を区別して設計単位を揃える。

**手順**:
1. 業務フロー・行動シナリオから、ユーザーのアクション／システムの働きを抽出
2. UI デザインの範囲外の「**システム外の事柄**」は設計対象外として一旦除外
3. ユーザータスクに**呼応するシステムの働き**を並べて書く（例: ユーザー「メールを受信する」↔ システム「サーバーから読み込む」）。働きはユーザー行動の結果＝因果でイメージ
4. 各タスクを **CRUD** で分類。Read は暗黙のことが多い → 明示操作でなければ **C・U・D 中心**。Delete は要注意（「ゴミ箱へ移動」は復元可能なら **Update**）

**タスク表の列**: ユーザー（アクション）／システム（働き＝Function 粒度）／CRUD（主体ごとに分けるなら CRUD 列を2つ）／対応ユースケース。Feature はユースケースとほぼ1対1なので、対応ユースケース列が Feature の括りを兼ねる。

**チェックポイント**（括弧内はよくある罠）:
- 「機能」は Feature / Function で粒度を区別する（罠: 粒度が曖昧）
- 表にはシステム内のタスクだけを載せる（罠: システム外のタスクの混入）
- タスクの**分岐条件**を、タスク表と別のメモ／簡易フローチャートに記録する（罠: 記録漏れ）
- Read は明示操作のときだけ定義する（罠: 暗黙の Read を無駄に定義）
- Delete はメンタルモデル＋データ構造を見て判定し、復元可能なら Update にする（罠: 誤分類）
- ①や③と行き来して都度拡充する（罠: 一気に完成させようとする）
