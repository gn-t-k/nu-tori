# 機能追加モード

[SKILL.md](SKILL.md) の種類が「機能追加」のときに読む。既存の UI に機能を足すとき、①〜⑦を最初から回さず、**現状モデル**に差分を積む。ブロックの進め方は SKILL.md の「ブロックを1つずつ回す」のまま。各ブロックのファイルを読み、工程ごとに下の表の読み替えを当てる。

## 現状モデルを組み立てる（①の前）

正本とコードから、今の UI のモデルを組み立て直して `00-current-model.md` に書く。前回の設計記録からは組み立てない（凍結後に変わっている可能性があるため）。ただし、まだ実装していない部分は、凍結した設計記録と、仕様にする前の決定（ルートの `AGENTS.md` の「情報の置き場」）から組み立てる。

- **概念オブジェクト**: `CONTEXT.md` の用語と、コードのデータ構造から。関連と多重度も、コードの型・スキーマから読み取る
- **ナビ**: ルーティングや画面遷移のコードから、ビューのツリーを描く
- **前提となる決定**: `docs/adr/` のうち、置き換えられていない設計思想・最重要コンセプト・ナビの根・フォームファクタと、まだ実装していない決定（「情報の置き場」）
- **見た目**: `DESIGN.md` の有無と、使える部品の一覧

完了条件: `CONTEXT.md` の全用語が概念オブジェクトとして現れるか、現れない理由が書いてある。ルーティングの全ルートがナビのツリーに現れる。

ペルソナは、過去の設計記録の `00-persona-model.md` がそのまま使えるならパスを参照として書き、変わるなら新しく作る。行動シナリオは追加分だけ書く。

## 工程の読み替え

| 工程 | 機能追加での扱い |
|---|---|
| ① ユースケース | 追加分だけ書く。既存の用途と重複しないか現状モデルと照らす |
| ② タスク | 追加分だけ書く |
| ③ 概念設計 | 追加するオブジェクトと関連を、現状モデルに書き足した形で `03-concept-model.md` に書く。既存の用語は `CONTEXT.md` の名前をそのまま使う |
| ④ コンセプト | `04-concept.md` は作らない。既存 ADR の設計思想と最重要コンセプトに照らして逸脱チェックだけ行い、結果を `index.md` に書く |
| ⑤ ナビ | 新しいビューを既存ツリーのどこにつなぐかを設計する。既存の経路の変更は差分として明示する |
| ⑥ レイアウト | フォームファクタは既存 ADR を前提にする。新しいビューを既存のレイアウトパターンに当てはめる |
| ⑦ 表現 | `DESIGN.md` のトークンと部品を使う。足りない部品だけ新しく作る |

## ゲートの読み替え

ゲートは**現状モデル＋差分の全体**で判定する。④を作らないので、④を参照する項目は次のように読み替える:

- 中盤ゲート「`04-concept.md` に4つの柱が揃い…」→「既存 ADR の設計思想・最重要コンセプトからの逸脱が0件」
- 中盤ゲート「目標地点が…④の最重要コンセプトと一致する」→「追加後もナビの根が既存 ADR のナビの根と一致する」
- 終盤ゲート「④の最重要コンセプトがファーストビュー1アクションで達成できる」→「追加後もそのまま達成できる」

## 再構築に切り替えるとき

差分では済まないと分かったら、ユーザーに種類を「再構築」に変えるか相談する。目安: 最重要コンセプトやナビの根を変える必要がある、既存の概念オブジェクトの大半の関連が変わる、フォームファクタが変わる。
