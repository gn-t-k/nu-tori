UI を「いきなり画面の絵」から作らない。情報の構造を段階的に**モデル**化し、矛盾を潰してから表現に落とす。出典は書籍『モデルベースUIデザイン 構造化UIと情報設計の方法論』。

## 核となる考え方

全工程をこの4語が貫く。

- **モデル** — 各工程は1つのモデル（設計図）を産む。次の工程はその前段モデルを材料にする。
- **ユースケース中心** — 「機能一覧」ではなく、ユーザーの用途（ユースケース）を**すべての設計の根拠**にする。後段の正否は常に「ユースケースに照らして必要か」で測る。
- **構造が先、表現が後** — UI は複雑で変わりやすい。確実に成り立つ構造を固めてから表現を探る。作業割合の見積もりは 構造 60% / インタラクション 30% / ルック&フィール 10%。見た目を先に作って後で辻褄を合わせると質が下がる。
- **ゲート** — 工程は3つのブロックにまとまる。各ブロックの**出口でゲート（整合性チェック＋人間承認）**を通すまで次のブロックへ進まない。これが「飛ばし」を防ぐ唯一の仕組み。順序ロックではなく、矛盾を潰す整合性チェックである。

## 用語

工程をまたいで出る基本語。ブロック固有語はそのブロックのファイルで定義する。

- **ユースケース** — ユーザーの用途。「〈誰〉が〈何〉を〈行動〉できる」構文で書く（①）。
- **概念オブジェクト** — UI で扱うコンテンツそのもの（レシピ、写真、ユーザー等の「もの」）。ボタン等の「UI コントロール」とは別物（③）。
- **単位ビュー** — 1つのユースケース/タスクを実現する、意味のあるビューのまとまり。概念オブジェクトのコンテンツ＋CRUD アクションを内包する。③のフレーム構造の単位であり、⑦のコンポーネントの単位でもある（粒度の詳細は block-2）。
- **モードレス** — ユーザーの行動を特定の状態（モード）に縛らない設計姿勢。本メソッドの基本価値（⑦で担保）。

## 進め方

- **ハイブリッド**: 各工程でエージェントが叩き台を作り、ブロックのゲートで人間が承認してから次へ進む。
- **並行・反復**: 同じブロック内の工程は並行してよい。前段に考慮漏れが見つかれば、序盤〜中盤の間はいつでも遡って加筆する（ゲートを再通過）。
- **永続化**: 成果物を `docs/ui-design/<トピック>/` に工程番号順で保存する。**開始時に保存先をユーザーに確認**する。
- **視覚化**: 図・ワイヤーの描き方は [visual-output.md](visual-output.md)、⑦の往復は [design-sync.md](design-sync.md)。視覚化する工程で参照する。

## 使い方（起動・中断・再開・行き来）

| 局面 | 動き |
|---|---|
| **呼び出し** | 新規 UI / 機能 / 既存 UI 再構築の設計を始めるとき `/model-based-ui-design`。最初にトピック名と保存先を確認する |
| **1セッションの範囲** | 基本は**1ブロック単位**（序盤→ゲート承認→中盤→…）。各ゲートが自然な停止点。小規模なら一気通貫も可 |
| **中断・再開** | 成果物は保存先に残る。再開時はまず `index.md` と既存ファイルを読み、「どのブロックまでゲート通過済みか」を把握して次の未完工程から続ける |
| **工程の行き来** | ブロック内は並行・反復。ブロック間はゲートで前進を律する。後段で前段の漏れに気づけば序盤〜中盤の間は遡って加筆。終盤の後戻りは手戻りが大きいので慎重に |

入力（行動シナリオ・ペルソナモデル）が無いまま呼ばれたら、序盤に入る前にユーザーに提供を求めるか、軽い環境調査で用意する（[block-1-foundation.md](block-1-foundation.md) 参照）。

## 成果物構成とインデックス

```
docs/ui-design/<トピック>/
  index.md                    インデックス（下記。ゲート通過ごとに更新）
  00-behavioral-scenarios.md  行動シナリオ（入力。環境調査の成果物）
  00-persona-model.md         ペルソナモデル（入力。想定ユーザーの人物像）
  01-use-cases.md             ユースケースモデル（一覧）
  02-tasks.md                 タスク表（CRUD）
  03-concept-model.md         コンテンツ構造（概念モデル＋多重度）
  03-frames/                  フレーム構造（枠組みワイヤーの HTML）
  04-concept.md               コンセプト（4つの柱）
  05-navigation.md            ナビゲーション構造（ツリー）
  06-layout.md                レイアウト設計図
  07-components/              単位ビューの HTML コンポーネント（DesignSync 対象）
```

`00-` は工程①の入力（環境調査の成果物）。これらは序盤に入る前に用意し保存する（[block-1-foundation.md](block-1-foundation.md) 参照）。`index.md` は再開と実装ハンドオフの両方を1枚で支える。**各ゲート通過ごとに更新**し、次を書く: 進捗（どのブロックまでゲート通過済みか）／成果物マップ（各ファイルが何で、何に依存するか）／キー決定（最重要コンセプト・キーオブジェクト・ナビの根・対象フォームファクタ）／「実装はここから読む」順序。

## 3つのブロック

各ブロックは「そのファイルを読んで工程を回す → 出口のゲートを通す（**ゲートの詳細は各ファイル末尾**）→ `index.md` を更新して次へ」。ゲートを通すまで次のブロックへ進まない。

### 序盤ブロック ＝ ① ユースケース定義 ＋ ② タスク整理

環境調査と基本設計。用途と行動を整理する。→ [block-1-foundation.md](block-1-foundation.md)

### 中盤ブロック ＝ ③ 概念設計 ＋ ④ コンセプト定義 ＋ ⑤ ナビゲーション構造設計

UI の構造設計。③④⑤は並行・反復し、出口ゲートの本体は⑤のナビ統合。→ [block-2-structure.md](block-2-structure.md)

### 終盤ブロック ＝ ⑥ プラットフォーム適合・レイアウト設計 ＋ ⑦ 表現設計

表現設計と大詰め。⑦の Claude Design 往復は [design-sync.md](design-sync.md)。→ [block-3-expression.md](block-3-expression.md)

---

完成をゴールにしない。「ソフトウェアは一生完成しない」。不確定な要素は仮実装し、出荷後のユーザビリティ検証を経て再び設計に立ち返り、品質を少しずつ高める。
