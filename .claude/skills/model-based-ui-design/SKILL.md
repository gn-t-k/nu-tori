UI を「いきなり画面の絵」から作らない。情報の構造を段階的に**モデル**化し、矛盾を潰してから表現に落とす。出典は書籍『モデルベースUIデザイン 構造化UIと情報設計の方法論』。

## 核となる考え方

全工程をこの4語が貫く。

- **モデル** — 各工程は1つのモデル（設計図）を産む。次の工程はその前段モデルを材料にする。
- **ユースケース中心** — 「機能一覧」ではなく、ユーザーの用途（ユースケース）を**すべての設計の根拠**にする。後段の正否は常に「ユースケースに照らして必要か」で測る。
- **構造が先、表現が後** — 確実に成り立つ構造を固めてから表現を探る。作業割合は 構造 60% / インタラクション 30% / ルック&フィール 10%。
- **ゲート** — 工程は3つのブロックにまとまり、各ブロックの出口に**ゲート（整合性チェック＋人間承認）**がある。ゲートは順序ロックではなく、矛盾を潰す仕組みである。

## 用語

工程をまたいで出る基本語。ブロック固有語はそのブロックのファイルで定義する。

- **ユースケース** — ユーザーの用途。「〈誰〉が〈何〉を〈行動〉できる」構文で書く（①）。
- **概念オブジェクト** — UI で扱うコンテンツそのもの（レシピ、写真、ユーザー等の「もの」）。ボタン等の「UI コントロール」とは別物（③）。
- **単位ビュー** — 1つのユースケース/タスクを実現する、意味のあるビューのまとまり。概念オブジェクトのコンテンツ＋CRUD アクションを内包する。③のフレーム構造の単位であり、⑦のコンポーネントの単位でもある（粒度は block-2）。
- **モードレス** — ユーザーの行動を特定の状態（モード）に縛らない設計姿勢。本メソッドの基本価値。
- **叩き台** — 各工程でエージェントが作る初版。人間はゲートでこれを直し、承認する。

## 手順

1. **トピックと保存先を決める**。ユーザーにトピック名を聞き、保存先 `docs/ui-design/<トピック>/`（既定）で良いか確認する。
2. **再開かどうか判定する**。保存先に `index.md` があれば読み、「どのブロックまでゲート通過済みか」を把握して、次の未完工程から再開する。
3. **入力を揃える**。行動シナリオとペルソナモデル（`00-` の2ファイル）が保存先に揃うまで①に入らない。揃え方は [block-1-foundation.md](block-1-foundation.md) の「入力」。
4. **ブロックを1つずつ回す**。各ブロックで次のループを回す:
   1. ブロックのファイルを読み、工程ごとに叩き台を作って保存先に書く。ブロック内の工程は並行・反復してよい
   2. ファイル末尾のゲートの各項目を、成果物を**数えて**判定する。満たさない項目は該当工程に戻って直す
   3. 判定結果（各項目の ✅/❌ と根拠）と成果物をユーザーに示し、**承認を得る**。承認がゲート通過の完了条件
   4. `index.md` を更新し、ユーザーに次のブロックへ進むか、ここで区切るか聞く

   | ブロック | 工程 | ファイル |
   |---|---|---|
   | 序盤 | ① ユースケース定義 ＋ ② タスク整理 | [block-1-foundation.md](block-1-foundation.md) |
   | 中盤 | ③ 概念設計 ＋ ④ コンセプト定義 ＋ ⑤ ナビゲーション構造設計 | [block-2-structure.md](block-2-structure.md) |
   | 終盤 | ⑥ プラットフォーム適合・レイアウト設計 ＋ ⑦ 表現設計 | [block-3-expression.md](block-3-expression.md) |

   1セッションは1ブロックが基本で、ゲートが自然な区切りになる。小規模なら通しで回してよい。

後段で前段の考慮漏れに気づいたら、序盤〜中盤の間は遡って加筆し、そのブロックのゲートを再判定する。終盤からの後戻りは手戻りが大きいので、遡る前にユーザーに相談する。

図・ワイヤーの描き方は [visual-output.md](visual-output.md)（③⑤⑥で参照）、⑦の Claude Design 往復は [design-sync.md](design-sync.md)。

## 成果物構成

```
docs/ui-design/<トピック>/
  index.md                    インデックス（ゲート通過ごとに更新）
  00-behavioral-scenarios.md  行動シナリオ（入力）
  00-persona-model.md         ペルソナモデル（入力）
  01-use-cases.md             ユースケースモデル（一覧）
  02-tasks.md                 タスク表（CRUD）
  03-concept-model.md         コンテンツ構造（概念モデル＋多重度）
  03-frames/                  フレーム構造（枠組みワイヤーの HTML）
  04-concept.md               コンセプト（4つの柱）
  05-navigation.md            ナビゲーション構造（ツリー）
  06-layout.md                レイアウト設計図
  07-components/              単位ビューの HTML コンポーネント（DesignSync 対象）
```

`index.md` は再開と実装ハンドオフの両方を1枚で支える。次の見出しで書く:

```markdown
# <トピック>
## 進捗        ゲート通過済みのブロックと日付、次に着手する工程
## 成果物マップ  各ファイルが何で、どのファイルに依存するか
## キー決定      最重要コンセプト／キーオブジェクト／ナビの根／対象フォームファクタ
## 実装はここから読む  実装者が読む順序
```

完成をゴールにしない。「ソフトウェアは一生完成しない」。不確定な要素は仮実装し、出荷後のユーザビリティ検証を経て再び設計に立ち返り、品質を少しずつ高める。
