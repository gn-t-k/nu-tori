## ③ 概念設計 → コンテンツ構造（概念モデル）＋ フレーム構造（枠組みワイヤー）

2つの成果物を産む。**コンテンツ構造**＝UI の「中身」（概念オブジェクトと関連）。**フレーム構造**＝UI の「枠組み」（中身を包む外枠、配置を省いた粗いワイヤー）。

### 手順A：コンテンツ構造（概念モデル）→ `03-concept-model.md`

1. 名詞/目的語から「関心の対象＝もの」候補を抽出
2. `CONTEXT.md` があれば、既にある用語はその名前を使う。新しい用語は引き継ぎで登録するので、`03-concept-model.md` で「新規」と印を付ける
3. **概念オブジェクトの要件**でふるう。すべて満たすものが概念オブジェクト:
   - 名詞で表せる「もの」である（コマンドやジェスチャーそのものではない）
   - 認知や操作の対象になり得る
   - CRUD の対象である
   - 複製でき、同種が複数存在し得る
   - **プリミティブな値（単なるテキスト・数値）ではない**
4. オブジェクト同士を**矢印でつなぎ「属性名」ラベル**を付ける（例: レシピ →〈構成材料〉→ 材料。双方向/片方向どちらも可）
5. 各関連に**多重度**を付ける。使うのは **4パターンのみ**（具体数値で縛らない）。多重度は後段⑤の表示パターンに直結するので必ず両端に付ける ── この対応表が多重度の唯一の定義箇所:

| 多重度 | 意味 | ⑤での表示パターン |
|---|---|---|
| `0..1` | 0 もしくは単数 | 単体ビュー ＋ 空表示 |
| `1` | 単数 | 単体ビュー |
| `0..n` | 0 以上 | 一覧ビュー ＋ 空表示 |
| `1..n` | 1 以上 | 一覧ビュー |

図の描き方は [visual-output.md](visual-output.md)。

### 手順B：フレーム構造（枠組みワイヤー）→ `03-frames/`

6. **単位ビュー**（1ユースケース/タスクを実現する意味のまとまり）を想定し、各概念オブジェクトのコンテンツを表現する要素を配置
7. ②の CRUD を使い、実行可能アクション（ボタン等）の置き場をビュー内に設ける
8. **粗いまま**に留める（着色・具体コンテンツ・詳細レイアウト・タイポは除外。枠線・ペイン・グローバルナビ枠だけ）。1単位ビューにつき1枚。描き方は [visual-output.md](visual-output.md)

> **単位ビューの粒度**: ⑤のナビ図に出る「一覧ビュー／詳細ビュー」はこれより細かいノード。複数のナビ上ビューが1つの単位ビューに畳まれることがある（`07-components/` のファイル数は単位ビューの数で決まる）。

**チェックポイント**（括弧内はよくある罠）:
- プリミティブな値はオブジェクトの属性に留める（罠: 粒度が小さすぎ）
- 多重度は4パターンだけで書く（罠: 具体数値で縛る）
- 全関連で単体・コレクションを考える: 0→空・n→一覧・最大1→単体（罠: 考慮漏れ）
- 将来の拡張に耐える広めの名前を付ける（罠: 狭い命名は将来コスト）
- デザインとエンジニアの語彙をシソーラス定義表で揃える ＝ DDD のユビキタス言語と同型（罠: 用語のブレ）
- プロパティはユースケースに必要な分だけ定義する（罠: モデル作りの自己目的化）

## ④ コンセプト定義 → コンセプト（4つの柱）

デザインの**「芯」**＝何を目指すかの指針。③⑤と並行し、設計を**導く側**になる。芯を欠くと後段の判断に拠り所がなくなり設計が脆くなる（雑な姿勢は UI に表出してユーザーに見透かされる）。だから定義して終わりにせず、以降ずっと逸脱チェックの基準として使う。産出物は `04-concept.md`。

**4つの柱**（各柱を「何を／なぜ／どう書くか」で）:

1. **提供したいユーザー体験** — *何*: ユーザーにどういう体験をして欲しいかの宣言。*なぜ*: チームが目指す価値を1つに揃える。*どう*: 一言で。「〜させる」と**断定せず**「〜になって欲しい」と丸める（断定すると設計がユーザーを縛る＝モーダルに傾く）。強制でなく理想像（得られないユーザーもいる前提で、できる限り実現を志す）。
2. **設計思想** — *何*: デザインで最も重視する考え方。*なぜ*: **後段でトレードオフが生じたとき「何を取り何を捨てるか」を決める指針**になる（すべての要求は満たせない）。*どう*: テキストで（例: お金を扱う→ユーザビリティを多少犠牲にしてもセキュリティ優先／若年層 SNS→万人受けを避けカジュアルに）。シンプル / モードレス / 拡張性もここに明示。
3. **何をするものか** — *何*: この製品で「できること」を端的に並べた大きなコンセプト。*なぜ*: ユーザーが製品で何ができるか掴みやすくする。*どう*: 箇条書き（メール例: 受信／下書きを編集／送信／複数メールボックスを管理／検索）。②タスク表と似るが、これは CRUD 分解ではなく**「できること」の粗い要約**。
4. **コンセプトイメージ** — *何*: 思い描く UI の姿の簡単な絵（落書きレベル可）。*なぜ*: イメージを具体化しチームの議論に活かす。*どう*: ③のユースケース/コンテンツ構造を参考に描く。見た目だけでなくインタラクション（操作とフィードバック）の様相もここから検討してよい。
   - ⚠️ **「いきなり絵を描かない」原則と矛盾しない**: 禁じているのは*精緻な見た目から作る*こと。落書きレベルで仮説を立てるのはむしろ有効。だから**粗く・捨てる前提**で描く。

**手順**: 概念オブジェクト/タスク/コンセプト（できること）のリストを用意 → タスクをコンセプトにぶら下げ依存関係を示す → UC・コンテンツ構造を参照し**最重要のタスク/オブジェクト**を評価して優先度を付ける → コンセプトイメージのラフスケッチ。

**逸脱チェックの運用**（④の本質）: コンセプトには**都度立ち戻る**。⑤で「最重要コンセプトがファーストビューで達成できるか」「能動/受動の温度感」、⑥で「最適フォームファクタの判断基準」、全工程で「今の設計が逸脱してないか」を確認する。守れないなら、コンセプトが無理難題すぎたか、軽視しているかのどちらか。

**チェックポイント**（括弧内はよくある罠）:
- 各工程で④に立ち戻る（罠: 定義して振り返らず芯を失う）
- ユーザー体験は「〜になって欲しい」で書く（罠: 断定してモーダル化）
- **最重要は1つに絞る**（罠: 複数立てて焦点がぼやける）

## ⑤ ナビゲーション構造設計 → ナビゲーション構造

情報への「経路」を作る。**「画面」でなく「ビュー」を単位**にし、枝葉（入口）→根（目標地点）に収束するツリーで表す。産出物は `05-navigation.md`。図の描き方は [visual-output.md](visual-output.md)。

1. **ボトムアップ式**: 概念オブジェクトの詳細表示を目標地点に置き、連なる動線を逆順（芋蔓式）に辿る。UC 照合で要否吟味
2. **トップダウン式**: グローバルナビ（タブ/サイドバー）の入口から始め、第2階層以降の概要一覧 → 各詳細へ接続
3. **多重度から表示パターンを推測**: ③手順Aの対応表に従う（`n`→一覧／最大`1`→単体／`0`→空）。基本は概要一覧→詳細（List-Detail）
4. **2図を重ねて差異解消**: 共通=維持／片方のみ=OR で一旦採用→吟味／UC 外=除外 or UC 遡及／大きな矛盾=その部分を作り直す

併用: 紙の上で決めきれない経路は `/prototype` で動くものを作って確かめる。

なぜ2方向か: 別角度で同じ構造を2回設計し、互いに挟み込んで精度を上げ堅牢にするため。

**チェックポイント**（括弧内はよくある罠）:
- 「ビュー」単位で考える（罠: 「画面」単位ではモーダル等の柔軟構造を表現できない）
- ナビは情報の経路として作り、レイアウトは⑥に回す（罠: レイアウトから作る）
- 同じ情報がどのタブからも辿れる重複を許容する（罠: **縦割り化**＝特定タブへの閉じ込め）
- 経路は今いるタブの中で完結させる（罠: タブジャンプ＝意図せぬタブ切替で現在地を失う）
- 詳細表示は通常のビューとして開き、回遊性を保つ（罠: 詳細表示のモーダル化）
