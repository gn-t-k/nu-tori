# フェーズ3: 表現方法の設計

- **ゴール**: 種別・区分を表で分けるか区分の列にするかと、変わる値・無いことがある値をどう表すかを決める
- **インプット**: フェーズ2の表の一覧と Mermaid の ERD
- **アウトプット**: 表現方法を決めた ERD と設計判断

フェーズ2は重複を除く機械的な作業で、正解が客観的に決まる。このフェーズの判断は、要件と将来の拡張に依る。

UPDATE と DELETE で値を書き換える設計は、既定では避ける。UPDATE と DELETE は過去の値を失わせ、将来の拡張を狭めるため。採るのは、クエリが書けないほど複雑になる、速さが致命的に落ちる、プロジェクトの決まりがそう定めている、のどれかのときだけ。

## 手順

### ステップ1: サブセットを決める

種別・区分のあるエンティティ（「〜の種類」「〜タイプ」「〜区分」がある、属性の違う変わり種がある）について、どちらで表すかを決める。

- **サブセットの表**: 共通の属性を親の表に、種別に固有の属性を子の表に置く。表の数が増え、管理するものが多くなる
- **区分の列**: 同じ表に `type` の列を置き、種別によって使わない列は NULL にする。NULL を許す列が増えて表が膨らみ、種別で分ける if がプログラムに増える

迷ったらサブセットの表にする。サブセットの表にするのは、次のどれかに当たるとき。

- 種別に固有の属性がある、または将来出てきそう
- 1つの実体が同時に複数の種別を持ちうる（法人の社長が個人の顧客でもある）
- 種別ごとにバリデーションや処理が変わりそう
- 種別が増えそう

区分の列で足りるのは、種別の違いがラベルや絞り込みの条件だけで、将来も属性に差が出る見込みがないとき。

| 例 | 判断 | 理由 |
|---|---|---|
| 投稿のメディア（テキスト・画像・動画） | サブセットの表 | 画像は解像度、動画は再生時間やサムネイルを持つ |
| 商品の販売の状態（販売中・停止） | 区分の列 | 属性に差がない |
| 決済の方法（カード・振込・コンビニ） | サブセットの表 | 方法ごとに要る情報が違う |
| 表示のテーマ（ライト・ダーク） | 区分の列 | ただの設定値 |

### ステップ2: 無いことがある値を決める

NULL を許す列のそれぞれに、`table-design-rules.md` の「値が無いことの表し方」の4つの種類を当て、分けるか許すかを決める。NULL を許す外部キーはフェーズ4に回し、パーキングロットに書く。

### ステップ3: 変わる値を決める

各属性について、次の順に決める。

1. 変えることや消すことがあるかを確かめる
2. あるなら、次に1つでも当たればイベントの表に分けることを検討する
   - 過去の値を見る画面・帳票・分析がある
   - 監査やコンプライアンスで変更の履歴が求められる
   - 変えた時機や理由を、あとから確かめたい
   - 変えることが、ほかのエンティティの状態に効く
   - 将来の要件で履歴が要りそう
3. どれにも当たらず UPDATE・DELETE で書き換えるなら、将来イベントの表が要る具体的な場面と、あとから移るときの互換を示し、ユーザーに委ねる

## 例

- SNS の投稿のメディア: 画像と動画に固有の属性がある → サブセットの表にする。今の要件で固有の属性を使わないなら、`posts` の `media_type` と `media_url` で始めて、固有の属性が要るときに分けるかをユーザーに確かめる
- EC の注文のステータス: 注文 → 決済 → 出荷と遷移する → 遷移ごとにイベントの表（`payments`、`shipments`）になっているかを確かめる
- EC の商品の価格: 変わる。注文したときの単価は明細が持つので、商品の価格は書き換えでよいか、「価格の改定の履歴を分析に使う場面はあるか」をユーザーに確かめる
- SNS のフォローの解除: DELETE の候補。「過去のフォローを分析に使う場面はあるか」をユーザーに確かめる
