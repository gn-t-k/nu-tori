# 表の設計ルール（フェーズ2以降）

## 値の範囲はアプリで確かめる

区分や値の範囲は、アプリのバリデーションで確かめる。RDB の enum 型と CHECK 制約は、値を足すたびに移行が要り、保守が重いため使わない。

## 分けるかは事実の数で決める

正規化や表の分割は、事実がいくつあるかで決める。「JOIN が増えてクエリが複雑になる」は分けない理由にしない。SQL が多少複雑になっても、エージェントを使えば読み解け、テストがあれば安全に直せ、適切なインデックスがあれば速さも問題にならない。考慮するのは、クエリが書けないほど複雑になるときだけ。

## 値が無いことの表し方

値が無いことは、NULL か、表の構造（イベントの表、サブセットの表、中間の表）で表す。空文字（`""`）・`0`・`-1`・`"N/A"` のようなセンチネル値は、ドメインの正当な値と見分けられないため、NULL の代わりの既定値にしない。

- センチネル値だと、「まだ入っていない」と「ユーザーが空文字やゼロを入れた」を区別できない
- NULL は SQL の標準（`IS NULL`、`COALESCE`）でそろって扱えるが、センチネル値は、読む人全員がその約束を知っていないと不具合になる
- 既定値にするのは、ドメインの正当な初期値だけ（例: `ordered_at DEFAULT CURRENT_TIMESTAMP`、`is_active DEFAULT true`）

NULL を許す列は、種類ごとに次のように扱う（フェーズ3で判断する）。

1. **NULL を許す日時の列**（`xxx_at`）: イベントの表に分ける（例: `read_at` → `readings`）。NULL を避けるためではなく、UPDATE を避けるため
2. **NULL を許す外部キー**（関連先が決まっていない）: 中間の表に分ける（フェーズ4で決める）
3. **NULL を許す属性**: 次の3つを確かめ、どれかに当たればサブセットの表に分け、どれにも当たらなければ NULL を許す
   - **3値論理**: WHERE・JOIN の条件・サブクエリの述語に使うか
   - **NULL の伝播**: 四則演算や集計関数に使うか
   - **速さ**: `IS NULL` で頻繁に探すか
4. **すべて入るか、すべて無いかの列の組**（例: 配送先の住所・市区町村・郵便番号）: サブセットの表に分ける

参考: https://mickindex.sakura.ne.jp/database/db_getout_null.html （NULL の害の説明に従う。デフォルト値で避ける方法は、上のセンチネル値の理由で採らない）

## 時刻の列は事実で名付ける

時刻の列には、その列が記録する事実の名前を付ける（`posted_at`、`reserved_at`、`paid_at`、`read_at`）。名前が浮かばないときは、その列が要るかを疑う。どの表にも一律に `created_at`・`updated_at` を付けることはしない。イベントの表では、日時の名前がエンティティの意味をはっきりさせる。

参考: イミュータブルデータモデル https://scrapbox.io/kawasima/イミュータブルデータモデル の「すべてのエンティティに付ける登録日時や更新日時」
