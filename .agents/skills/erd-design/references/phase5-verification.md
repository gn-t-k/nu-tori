# フェーズ5: 検証

- **ゴール**: フェーズ1〜4で作った ERD の全体で、要件を読み書きできるかを確かめ、設計の問題を見つける
- **インプット**: フェーズ4までの ERD、設計判断、要件サマリーとユースケース
- **アウトプット**: 要件を満たすことを確かめた最終の ERD と設計判断サマリー

フェーズ2〜4で統合・分割・属性の移動が起きるので、フェーズ1で満たしていた要件が最終の ERD で書けなくなっていることがある。このフェーズでは、個々の判断ではなく全体の整合を見る。

## 手順

### ステップ1: 擬似 SQL で要件を確かめる

範囲のユースケースを1つずつ辿り、最終の ERD の表と列で書けることを擬似 SQL で示す。目で見て「書けそう」と判断すると、JOIN の道の欠け、列の漏れ、多重度の誤りを見落とすため。

1. 要件サマリーと要件の出どころから、範囲のユースケースを並べる
2. ユースケースごとに、読む（SELECT: 見せるデータを取れるか。JOIN の道が通り、絞り込む列があるか）と書く（INSERT: 起きたデータを保存できるか。要る列がそろっているか）の擬似 SQL を書く。どの表を JOIN し、どの列で絞るかが分かればよく、厳密な構文でなくてよい
3. 範囲が差分なら、既存の表を変えるところを、プロジェクトの移行の決まりで書けるかも確かめる
4. 出力ファイルの「要件の検証」に、擬似 SQL と結果（OK・NG）を書く。NG は「⚠️ 要確認」にする

例（EC の受注）:

| # | ユースケース | 擬似 SQL | 結果 |
|---|---|---|---|
| 1 | 複数の商品を注文する | `INSERT INTO orders (...); INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES (...), (...)` | OK |
| 2 | 注文明細を小計つきで見せる | `SELECT oi.*, oi.unit_price * oi.quantity AS subtotal, p.name FROM order_items oi JOIN products p ON p.id = oi.product_id WHERE oi.order_id = ?` | OK |
| 3 | 決済を記録する | `INSERT INTO payments (id, order_id, method, amount, paid_at) VALUES (...)` | OK |

### ステップ2: よくある誤りを探す

- **重すぎる**: 今の要件に要らない表や属性、「将来要るかも」だけで足した表がないか。DB だけで解こうとせず、プログラムとの分担を考えたか
- **パターンの当てはめ**: ヘッダとディテール、中間の表などを、要件に照らさず当てはめていないか。どの表も「なぜこの形か」を説明できるか
- **聞き取りの不足**: 多重度を「たぶん 1:N」で決めたところ、サブセットの将来の拡張、導出項目を持つか外すかの業務のルールを、ユーザーに確かめずに埋めていないか

### ステップ3: 構造の整合を確かめる

- 表と列の命名（複数形・単数形、snake_case など）がそろい、既存のスキーマと合っているか
- NULL を許す列に、「値が無いことの表し方」の判断が記録されているか
- UPDATE・DELETE で書き換える列に、将来の履歴の場面、ユーザーの確認、互換の評価が記録されているか
- 自己参照（親子、フォロー）のほかに、表の参照が循環していないか

### ステップ4: 最終の ERD を書く

出力ファイルの「フェーズ5」の「最終の ERD」に、最新の Mermaid の ERD を書く。

## ユーザーに確かめること

ステップ1〜3で決めきれないものを「⚠️ 要確認」にする。無ければ「セルフレビューで問題なし」と返す。
