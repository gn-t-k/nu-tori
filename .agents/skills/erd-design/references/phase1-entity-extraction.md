# フェーズ1: エンティティの抽出

- **ゴール**: システムが記録するデータのまとまり（エンティティ）を洗い出す
- **インプット**: 要件サマリーの範囲と、要件の出どころ（ユースケース、画面の仕様、概念モデル、既存のデータ）
- **アウトプット**: エンティティの一覧（名前・種別・主な属性）

範囲が差分なら、範囲の要件に出てくるエンティティだけを扱い、既存の表は参照先として一覧に添える。概念モデルがあれば出発点にし、足した・外した・分けたエンティティを理由つきで書く。

## イベント系とリソース系

| | イベント系 | リソース系 |
|---|---|---|
| 表すもの | 起きたこと | 在るもの |
| 見分け方 | 「〜する」「〜日」が言える（注文する、注文日） | 「〜名」が言える（ユーザー名） |
| 例（EC） | 注文、出荷、返品、決済 | ユーザー、商品、配送先 |
| 例（SNS） | 投稿、いいね、フォロー、通報 | ユーザー、コミュニティ、タグ |

イベント系から先に抽出する。イベント系は「ユーザーが何をするか」から直接見つかり、リソース系はイベントの「誰が」「何を」「どこで」から浮かび上がる。リソースから始めると、どのイベントにも使われないエンティティを作りやすい。

## 手順

### ステップ1: エンティティを洗い出す

1. ユーザーの行動を並べる（何をするか、誰が関わるか、何に対してするか、どんな種別や区分があるか）
2. 「〜する」「〜日」でイベント系を見つける
3. イベント系の「誰が」「何を」「どこで」からリソース系を見つける

### ステップ2: 属性を並べる

各エンティティの主な属性を、次の観点で漏れなく並べる。型はまだ決めず、重複の整理はフェーズ2で行う。

| 観点 | 例 |
|---|---|
| いつ（日時） | 注文日時、公開日時 |
| いくつ（数量） | 数量、閲覧数 |
| いくら（金額） | 価格、値引額 |
| なぜ（理由・状態） | キャンセルの理由、ステータス |
| 誰が・何を（参照） | ユーザー、商品、投稿 |

### ステップ3: 見落としたイベントを探す

- **入と出の対**: 入金と出金、フォローとアンフォロー、注文とキャンセル
- **状態の遷移**: 注文 → 決済 → 出荷 → 配達 →（返品）。各状態は別々の事実なので、それぞれをイベント系のエンティティにする。1つのエンティティに状態を混ぜると、状態ごとの属性を見落とす
- **あるときだけ値が入る属性**: 既読日時 → 既読のイベント、キャンセル日時 → キャンセルのイベント、削除日時 → 削除のイベント
- **前後のイベント**: 予約があれば、あとにチェックインがあるはず。訂正があれば、前に訂正されるものを作ったイベントがあるはず

## このフェーズで扱う問い

判断は、エンティティの単位で語る（「別の事実として記録すべきか」「誰が・いつ・何に対して起こすか」）。表の構造（NULL、UPDATE と DELETE、正規化）はフェーズ2・3、関係の多重度はフェーズ4で扱い、ここで出た話はパーキングロットに書く。

## 例: EC の受注

要件: 顧客が商品を注文する。1回の注文で複数の商品を買え、合計に送料と消費税が加わる。

- 行動: 注文する、決済する、出荷する、返品する
- イベント系: 注文、注文明細、決済、出荷。リソース系: ユーザー、商品、商品カテゴリ、配送先
- 属性の例: 注文（ユーザー、配送先、合計金額、送料、税、注文日時）、注文明細（注文、商品、数量、単価）
- 見落とし: 注文 → 決済 → 出荷の先の「配達完了」、返品に対する「返金」→ 要件を確かめる
