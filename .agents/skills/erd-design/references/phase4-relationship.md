# フェーズ4: 関係の設計

- **ゴール**: エンティティのあいだの多重度（1:1、1:N、N:M）を決め、外部キーと中間の表を置く
- **インプット**: フェーズ3の ERD と、パーキングロットの NULL を許す外部キー
- **アウトプット**: 多重度を決めた Mermaid の ERD

## 手順

### ステップ1: 多重度を決める

2つのエンティティごとに「A から見て B は複数あるか」「B から見て A は複数あるか」を問う。

- 1つと1つ → 1:1。片方に外部キーを置く
- 複数と1つ → 1:N。N の側に外部キーを置く
- 複数と複数 → N:M。中間の表を置く

Mermaid の記号は、相手が0件でもよいかで選ぶ。

| 記号 | 意味 | 例 |
|---|---|---|
| `\|\|--o{` | 1 対 0 以上 | ユーザー → 投稿 |
| `\|\|--\|{` | 1 対 1 以上 | 注文 → 注文明細 |
| `\|\|--o\|` | 1 対 0 か 1 | 注文 → 決済（まだ払っていない注文がある） |
| `\|\|--\|\|` | 1 対 1 | 必ず対になるもの |

### ステップ2: 中間の表を置く

N:M には中間の表を置き、両方の ID を外部キーに持たせる。関係の事実に属性があれば中間の表に持たせる（`user_roles` の `granted_at`・`expires_at`、並び順など）。

- UNIQUE 制約の付け方で、1:1 にも 1:N にも N:M にも変えられる
- 開始と終了の日時を持たせれば、関係の履歴を残せる
- 同じ表を2回参照してもよい（`follows` の `follower_id`・`followee_id`、カテゴリの親子）

### ステップ3: 依存しない関係を確かめる

1:N でも、両者が互いに依存しないなら、N の側に外部キーを直に置くと、関連が決まらないあいだ NULL になる。

依存を確かめる問いは「A が無くても B は在りうるか」「B がどの A にも結び付かない状態はありうるか」。両方に「はい」なら依存しない関係なので、中間の表を置く。1:N を保つなら、中間の表の片方の外部キーに UNIQUE 制約を付ける（N:M に変えるときは制約を外すだけで済む）。

| 例 | 依存 | 扱い |
|---|---|---|
| 部門と社員 | しない（配属の前の社員、部門に属さない役員） | 「所属」の中間の表を置く |
| 注文と注文明細 | する（明細は注文なしに無い） | 外部キーを直に置く |
| 記事と著者 | しない（著者の決まっていない下書き） | 「執筆」の中間の表を置く |

参考:
- イミュータブルデータモデル Step5: https://scrapbox.io/kawasima/イミュータブルデータモデル
- 1:N でも中間の表を検討する: https://zenn.dev/praha/articles/65afb28caacd0b

## 例

- SNS: ユーザー → 投稿は 1:N、フォローはユーザーどうしの N:M（`follows` が同じ表を2回参照する中間の表）、投稿 ↔ タグは N:M（`post_tags`）
- EC: 注文 → 注文明細は 1:1 以上、注文 → 決済は 1 対 0 か 1。注文 → 出荷は、分けて出荷するなら 1:N になるので要件を確かめる
