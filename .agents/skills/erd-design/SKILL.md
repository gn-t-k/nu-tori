# ERD の設計

要件から RDB の表の構造（ERD）を5つのフェーズで設計する。このファイルに従うメインのエージェントは、フェーズを進めることとユーザーとの対話を受け持つ。各フェーズの作業は、フェーズごとに新しいサブエージェントに任せる。フェーズのファイル（`references/phase*.md`）はそのフェーズのサブエージェントに渡し、メインはフェーズについて出力ファイルとサブエージェントの返却を読む。先のフェーズの手順が目に入ると、今のフェーズを急ぐため。

## 原則

- **段階を踏む**: 各フェーズは、そのフェーズの問いにだけ答える。完成した ERD は5つのフェーズを通して作る
- **出力ファイルが正本**: 設計の状態、判断、議論ログは、ラウンドのたびに出力ファイルに書く。コンテキストが消えても、出力ファイルから再開できる状態にする
- **確かめるときは選択肢で**: ユーザーには、具体的な選択肢とそれぞれの pros/cons を示して尋ねる
- **先のフェーズの話はパーキングロットへ**: 今のフェーズの外の指摘は、出力ファイルの「パーキングロット」に書き、そのフェーズで扱う

## 始める

1. 範囲をユーザーと決める
   - **全体**: システム全体の表を設計する
   - **差分**: 既存のスキーマに、機能や仕様の分の表を足す・変える。範囲の外の表は動かさない前提にし、既存の表を変えるなら、プロジェクトの移行の決まりで書けるかをフェーズ5で確かめる
2. Explore のサブエージェントに範囲を渡し、表の形を縛るものを調べる
   - プロジェクトの決まり: ADR、ルートとサブディレクトリの `AGENTS.md`、そこから指す文書のうち DB に関わるもの（使う DB と型、命名、移行の決まり、表の設計の進め方と出力ファイルの置き場）
   - 既存のスキーマ（移行の SQL、ORM のスキーマなど）の命名と構造。差分なら、範囲に関わる既存の表
   - 範囲の要件の出どころ: ユースケース、画面の仕様、概念モデル、用語集
3. 出力先のディレクトリをユーザーに尋ねる。2で置き場が見つかれば、それを案として示す。ファイル名の既定は `erd-design.md`
4. `references/output-template.md` から出力ファイルを作り、1で決めた範囲と2で調べたことを要件サマリーに書く
5. 表の形に効く外部サービスが決まっているかを尋ねる。決まっていれば「外部サービス依存」に書き、決まっていなければフェーズ1の前に決める
   - 認証（Better Auth、Clerk など）: 管理される表（user、session など）が前提になる
   - 決済（Stripe など）: 持つ ID の体系（payment_intent_id など）が決まる
   - ファイルの置き場（S3、R2 など）: URL やキーの持ち方が決まる
   - メール・通知（SendGrid、FCM など）: 通知の表に効く
   - ほかに表の形に効くもの

「始める」は、要件サマリーと外部サービス依存が埋まったら終わる。

## フェーズを回す

フェーズ1から5まで、順に次を繰り返す。

1. 下の起動テンプレートでサブエージェント（general-purpose）を起動する
2. 返却と出力ファイルを確かめる。テンプレートの「やること」に済んでいないものがあれば、それを追加の指示にして手順1へ戻る
3. 返却をユーザーに見せる
   - フェーズ1: エンティティの一覧、設計判断、⚠️ 要確認。⚠️ 要確認への答えとは別に、一覧の全体への意見を求める
   - フェーズ2〜4: ⚠️ 要確認があるときだけ見せる。無ければ手順5へ進む
   - フェーズ5: 全フェーズの設計判断サマリーと、最終の ERD
4. ユーザーの答えと指摘を、今のフェーズの議論ログに書く。反映するものがあれば、それを追加の指示にして手順1へ戻る
   - 今のフェーズの指摘は、今のフェーズのサブエージェントで直す。前のフェーズの前提が崩れたら、そのフェーズまで戻って回し直す
   - フェーズ5で出た指摘は、直すところが属するフェーズのサブエージェントで直し、フェーズ5を起動し直して検証し直す
5. フェーズの終わりを確かめる。満たさなければ手順3へ戻る
   - フェーズ1と5: ユーザーがはっきり承認した（「OK」「進めて」など）。⚠️ 要確認に答えただけでは終わらない
   - フェーズ2〜4: ⚠️ 要確認がすべて答えられ、出力ファイルに反映されている

ラウンド（サブエージェントの返却と、それに続くユーザーとのやりとり）の終わりには、ステータスを見せる。

```
**ステータス**
- 今のフェーズ: X/5（フェーズ名）
- エンティティの数: イベント系 N / リソース系 N
- 次にすること: [次のフェーズ、または今のフェーズで直すこと]
```

| フェーズ | リファレンス |
| --- | --- |
| 1. エンティティの抽出 | `references/phase1-entity-extraction.md` |
| 2. 正規化 | `references/phase2-normalization.md` |
| 3. 表現方法の設計 | `references/phase3-representation.md` |
| 4. 関係の設計 | `references/phase4-relationship.md` |
| 5. 検証 | `references/phase5-verification.md` |

### 起動テンプレート

`{...}` はメインが埋める。

```
ERD の設計のフェーズ{N}を行ってください。

## 読むファイル
スキルのファイルは次のものだけを読んでください。要件の出どころと既存のスキーマは、出力ファイルの要件サマリーが指すものを読んでください。
- 共通ルール: references/general-rules.md
{フェーズ2以降だけ: - 表の設計ルール: references/table-design-rules.md}
- このフェーズのリファレンス: {リファレンスのパス}
- 出力ファイル: {出力ファイルのパス}（今の設計の状態。結果をここに書き戻す）

## やること
1. 出力ファイルを読み、今の設計の状態、要件サマリー（範囲とプロジェクトの決まり）、設計判断を把握する
2. パーキングロットのうち、このフェーズの項目を扱う
3. 読んだルールを守りながら、リファレンスの手順でフェーズの作業をし、結果を出力ファイルのこのフェーズの節（Mermaid の ERD があれば ERD も）と「設計判断サマリー」に書く
4. リファレンスのセルフレビューと、読んだルールのファイルのセルフレビューを、すべての項目で当て、外れたものを出力ファイルの上で直す
5. 出力ファイルの「ステータス」を更新する

## 判断に迷うところ
- 要件を知らないと決められないところは、暫定の判断を置き、「⚠️ 要確認」を付ける
- フェーズの作業は最後まで終える

## 返すもの
1. このフェーズで変えたことの要約
2. 設計判断の一覧（判断と理由）
3. 「⚠️ 要確認」の一覧
{追加の指示}
```

## 再開する

途中から再開するときは、出力ファイルを探す（場所が分からなければ、既定の名前 `erd-design.md` で探すか、ユーザーに尋ねる）。見つけたら次の順に読み、終わっていないフェーズの「フェーズを回す」から続ける。

1. 「ステータス」で今のフェーズ
2. 最新の Mermaid の ERD で今のエンティティの構成
3. 「議論ログ」の最新のラウンドで、止まったところ
4. 「設計判断サマリー」で合意した判断
