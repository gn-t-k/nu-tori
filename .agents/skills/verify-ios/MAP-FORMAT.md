# 地図の機能のファイルの形

`features/` の機能のファイルを足す・直すときの形。節の並び、書くものと書かないもの、Issue の受け入れ条件から移す手順は、サーバーの地図の `../verify-server/MAP-FORMAT.md` に従い、`verify-server` を `verify-ios` に読み替える。ここには、アプリの地図で違うところだけを書く。

- `How to get to it (user POV)` の入口は、どの画面のどれを押すか（accessibility identifier か、画面に出る文字）で書く。受け入れ条件の入口にある端末が呼ぶ API は、アプリの地図には移さない
- `Driving it with verify-ios` の項目は、下の「確かめ方の書き方」で書く
- 受け入れ条件から移すときに足す確かめ方は、UI テストのクラス、または開く場面と押す要素

## 確かめ方の書き方

- UI テストのある入口は、手順を書き直さず、`$S/ui-test.sh <クラス>` を書く。クラスのメソッドの一部だけがその入口に当たるときは、メソッドの名前も書く。見える結果は、そのテストが確かめる画面の要素を、ユーザーの言葉で1行にする。この行を回すか全件の回で指すかは `SKILL.md` の確かめ方の1
- UI テストの無い入口は、`$S/launch.sh "$run" <アカウント> <API の場面>` で開く場面と、MobileBuildMCP で押す要素と、操作のあとに見える要素と値を書く
- UI テストを足した・名前を変えたら、地図の行も直す
