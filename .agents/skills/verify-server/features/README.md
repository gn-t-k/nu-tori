# サーバーの機能の地図

サーバーの、ユーザーから見た機能の索引。確かめる前にここを読み、触れた機能のファイルを手順として使う。機能がどこにあり、ユーザーがどうたどり着くかを知りたいときの索引でもある。

## 前提

- `start.sh` で空の状態から立てた回を使い、`doctor.sh` が全部 `ok` を返してから動かす
- アカウントは手順ごとに `sign-in.sh` で新しく作る。前の手順の記録に頼らない
- 書き込む値は作り話にする（公開リポジトリ）。体重は 60.5 kg、文章は `server/e2e/` の文面のような、誰のものでもない値

## 動かし方の決まり

- 手順の要求は、書いたとおりに送る。値を変えてよいのは、ID と時刻だけ
- 時刻は、書き込みではミリ秒（`$(date +%s)000`）、目標の設定の `--as-of` では ISO 8601
- 手順の `date` は GNU の形で書いてある。macOS では `-d` の相対の時刻を `-v` に置き換える（`<±N> days` は `-v<±N>d`、`<±N> minute` は `-v<±N>M`。項がいくつもあれば `-v` を並べる）
- 結果は `pull.sh` の出力を `jq` で絞って読む。応答の全文を読み込まない

## 証拠と、確かめていない入口

- 手順ごとに、操作と、そのあとに見えた状態（届いた記録、続く要求の状態コード）の両方を残す
- 入口を通せなかったら、試したコマンドと、揃わなかった前提を書く。別の入口で通したことを、その入口を確かめたことにしない

## 機能のファイルの形

1行目に見出し、続けてユーザーから見た振る舞いを1段落で書く。そのあとに次の4つの節をこの順で置く。

1. `Sub-features`: 短い ID と、1行の振る舞い
2. `How to get to it (user POV)`: ユーザーがたどり着く入口を全部。アプリの操作と、そのとき端末が呼ぶ API
3. `Driving it with verify-server`: `Preconditions:` で始め、操作ごとに、送るコマンドと、見えれば動いたと言える結果を対にする
4. `Gotchas`: 確かめを無駄にする、または無効にする罠

作りの説明は書かない。書くのは、ユーザーの経路、送る要求、要る状態、見える結果だけ。いまある機能だけを書き、予定の機能は書かない（`/pstack:maintain-verification-skill` が、アプリと食い違う地図をずれとして扱うため）。

## 機能

- [サインインとアカウントの削除](./account.md): 新しいアカウントで使い始め、アカウントと記録をすべて消すと、そのセッションが使えなくなる
- [体重記録](./weight-record.md): 手で記録した・ヘルスケアから取り込んだ体重記録が届き、体重の傾向が出る。直す・取り込み元で消す
- [目標の設定](./goal-setup.md): 目標の下見、目標案、目標を決めると、1日の目安と推定消費カロリーが届き、次の取りに行く要求で週の見直しが届く
- [食事の記録と推定](./meal-estimation.md): 撮った・撮っておいた写真の食事、文章の食事を送ると推定が進む。料理の名前を直す、食事を消す
- [送った文章と返事](./reply.md): 送った文章が読み分けられ、会話なら返事が見守る要求と取りに行く要求で届く。送り直す
